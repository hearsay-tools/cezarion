# Backward compatibility — protected surfaces

cezar is a published npm CLI (`@wjarka/cezarion`, currently 0.x, installed as `npx cezarion` — this clone took its own npm identity in #23 and has never published under upstream's `@open-mercato/cezar` or `cezar-cli` names) whose state lives as plain files inside users' repos. Users upgrade with `npx cezarion@latest` against `.ai/cezar/` directories written by older versions, and they script the CLI and hand-edit the files — the README promises "plain JSON, NDJSON and Markdown you can `cat` and fix by hand." That promise is the compatibility contract.

**Owner-approved exception — hearsay-tools/cezarion#1543:** the generated follow-up inbox is removed outright in 0.17.0, without the minor-release deprecation window below. Its todo routes, generation inputs, capability and SSE events are no longer protected. Existing `todos.json` files are never read, rewritten or deleted by the upgrade. Export them with `cp .ai/cezar/todos.json ./cezar-followups-export.json`; create ordinary tasks for selected work. `CEZ_FOLLOWUPS` is retired, and `CEZ_TODOS_FILE` is shadowed empty in agent environments. Historical `generateFollowups` run fields remain readable but have no effect. Notes, the handoff journal, Continue, live conversation follow-ups and worker inbox are independent and remain protected.
**General rule for every surface below:** additive changes (new optional field, new flag, new route) are fine; anything that makes an existing input rejected, an existing output disappear, or an existing file unreadable is breaking. While the package is 0.x, a breaking change requires: a deprecation note in the README + CHANGELOG, a migration path (code that reads the old shape, or a documented manual fix), and a **minor** version bump called out as breaking. From 1.0 on, breaking = major bump.

## 1. CLI commands, flags and exit codes (`packages/cezar/src/index.ts`)

- **Bins:** `cezarion` and `cez` (both in `package.json` `bin`). Removing either alias is breaking. Upstream's `cezar` and `cezar-cli` bins are deliberately absent here (#23) so a global install of this clone cannot shadow the upstream tool; that is the identity split, not a regression to repair.
- **Commands:** bare invocation = `serve` (cockpit); `cez run "<task>"`; `cez init`.
- **Cockpit ownership (#552):** `serve` exits 1 with the running cockpit's URL when its canonical data directory is already owned. Ownership is acquired before run recovery and lasts until process exit; dead-owner locks are reclaimed automatically. Different data directories remain independent. A project-scoped request for a secondary directory owned by another cockpit returns 409 with `{ error }` and that URL.
- **`cez discover` (#491):** `runners` returns default-account status/enablement using `runner` names; `models --runner=<id>` returns the existing host model catalog, including optional per-model `effortLevels`. No effort field means unknown, not a generic fallback. Exit codes: `0` success (including an unavailable catalog response), `2` unavailable/refused transport, `64` invalid usage. Operators use the existing cockpit discovery (`--repo`, `--url`, `CEZ_URL`); parent sessions use their private controller and never fall back after a credential failure.
- **Runner flag (hearsay-tools/cezarion#632, additive):** `cez task start` and `cez worker spawn` accept `--runner <id>` for every runner id, matching workflow `runner:`, the run API and `cez discover --runner`. `--backend` stays a permanent, documented alias with identical behavior and no deprecation warning, because the callers are bots that do not read stderr; removing it is breaking. The same value on both flags is accepted. Different values are a usage error naming both values: `task start` exits `64`, `worker spawn` exits `1` like every other `cez worker` `invalid_input`. The flag layer is the whole change: `--runner` fills the existing `backend` field of the worker spawn request, so a retry that switches spelling under one request id keeps its spawn request hash and dedupes. **Deliberate gap:** the flag says runner, but worker `inspect`/`collect` output and the spawn request keep the historical field name `backend`. Those shapes are contract schemas, and collected results are persisted, so renaming the field would break existing readers.
- **`cez task` subcommands (#504):** `start`, `list`, `status`, `log`, `wait`, `send`, `stop`, `finish`, `diff`, `open`, each printing one JSON object (`log` one JSON line per event). Exit codes are the contract: `0` ok (`wait`/`start --wait`/`log --follow`: `done`/`review`, or stopped for attention), `1` failed/cancelled or not delivered, `2` no cockpit / refused, `3` timed out, `64` usage error. `CEZ_URL` overrides discovery.
  - hearsay-tools/cezarion#554 widens accepted forms to allow COMMON flags (`--url`, `--repo`, `--help`/`-h`) before the operation; every previously valid invocation parses the same, while shared flags repeated before or across the operation are usage errors.
  - **Additive default projections (#573):** `list` rows include `currentStepId` when running, `pullRequestUrl` when done/review, and `error` when failed, each only when defined. Row errors are first-line only, capped at 200 characters including a trailing `…` whenever cut; `status` retains the full error. Default `status` always adds `handoffUrl`, the project-scoped `/api/v1/p/:projectId/runs/:id/handoff` URL, even when no contents are seeded. `branch`, `diffStat` and `tokensUsed` stay on `status`; `--full` remains the unmodified contract.
  - **`--until` default changed to `attention` (#553, #609; deliberate, not a regression).** `wait` and `start --wait` used to default to `settled` (terminal status only), which made every interactive `start --wait` time out (exit 3) once the agent parked as `waiting`. They now default to `attention`: the wait also ends when the cockpit's attention function puts the run in `waiting`/`error`/`permission` — the same `deriveAttention` the cockpit's Needs You reads, now in `packages/contract/src/attention.ts`. A root parked on its own workers and a `running`/`monitoring` run do not end it. **Migration:** a bot that wants terminal state only passes `--until settled` explicitly; its meaning is unchanged. No env var or config key restores the old default — the old default was the bug. `start` gained `--until` for the same choice. Additive output: default `status`/`list` rows and every run in the `wait` output carry `attention` (bucket) and `attentionLabel` (phrase); the `wait` output and the `start --wait` object carry `until`. `--full` output is unchanged. Clear contract: `waiting` is attention even when `hasPendingHumanAsk` is false; `running` + `activity: monitoring` is neither settled nor attention.
  - **`log --follow` gained `--until`, default `attention` (#931; deliberate, not a regression).** `log --follow` used to end only on a terminal status, so following an interactive task streamed until the timeout and exited 3 once the agent parked as `waiting`. It now takes `--until <attention|settled>` with the same default, the same `endsWait` predicate and the same exit codes as `wait` (`0` done/review or stopped for attention, `1` failed/cancelled or the run vanished, `3` timed out); a root parked on its own workers and a `running`/`monitoring` run do not end it. The CLI reads `GET /runs/:id` after the replay and on each attention-relevant change of a `run` frame; no route or stream changed. **Migration:** a bot that wants terminal state only passes `--until settled`, which keeps the old behaviour. `--until` without `--follow` is a usage error (exit 64). Additive output: the final `--follow` line (and its timeout line) now carries `attention`, `attentionLabel` and `until` beside `id`, `status` and `timedOut`. Every event is still printed before it. `log` without `--follow` is unchanged.
- **`cez automation` subcommands (hearsay-tools/cezarion#774, additive):** `schema`, `create`, `add`, `update`, `check`, `run`, `list`, `show`, `enable`, `pause`, `delete`, each printing one JSON object (`schema` prints the plain-text definition reference). Exit codes follow `cez task`: `0` ok, `1` a check that ended in error, `2` no cockpit or refused (including the `409` while `CEZ_AUTOMATIONS` is off, relayed verbatim), `3` a check that did not finish in time, `64` usage error. The cockpit address comes from `CEZ_COCKPIT_URL` + `CEZ_PROJECT_ID`, which the cockpit sets in every agent's env once it listens; only `--url`, `--repo` or `CEZ_URL` run discovery. The command never starts a server.
- **`cez projects` subcommands:** `list` (the default), `add`, `remove`/`rm`, `tag`. `tag <id> [<tag>…]` replaces a project's grouping tags wholesale; naming none clears them.
- **Flags:** `-p/--port` (default 4321; exact port, or OS-selected ephemeral port for `0`), `--repo <dir>`, `--workflow <name>` (default `quick-task`), `--model <model>`, `--no-open`, `-h/--help`.
- **Deliberate port behavior change (hearsay-tools/cezarion#722):** `serve` no longer scans subsequent ports when the requested port is occupied. It exits 1 with instructions to open the existing cockpit, stop the occupant or explicitly select a free port. The actual listener is acquired on `--bind-host` (default `127.0.0.1`) after directory ownership and before workspace initialization, worktree pruning, run recovery or background resources; it stays bound through application initialization. Free default/explicit ports, `--port 0`, same-directory ownership and application-update exact restart acknowledgements retain their behavior. **Migration:** choose `--port <free-port>` for a deliberate second cockpit, or `--port 0` for an ephemeral listener. No config or state migration is required.
- **Exit codes:** `run` exits 0 on `done` **and** `review` (spec 009 — headless runs must not hang on the review gate), 1 on `failed`/`cancelled`/unknown workflow. CI scripts depend on this.
- **Env vars:** `CEZ_DRY_RUN`, `CEZ_AGENT_MODELS_LOCKED`, `CEZ_APPROVAL_GATE`, `CEZ_CLAUDE_PERMISSION_MODE`, `CEZ_CLAUDE_SETTING_SOURCES`, `CEZ_HIDE_TOKEN_USAGE`, `CEZ_HIDE_COST`, `CEZ_HIDE_TOKEN_METRICS`, `CEZ_CLAUDE_BIN`, `CEZ_CODEX_BIN`, `CEZ_OPENCODE_BIN`, `CEZ_AGENT_TMPDIR`, `CEZ_URL`, `GITHUB_TOKEN`. Set by the cockpit for agents, not by users: `CEZ_COCKPIT_URL`, `CEZ_PROJECT_ID` (hearsay-tools/cezarion#774).
  - `CEZ_AGENT_TMPDIR` (#785) is an **opt-out** for a changed default, not a new feature switch: spawned agents now receive `TMPDIR`/`TEMP`/`TMP` pointing at this run's own repo-local directory (`.ai/cezar/t/<first 8 chars of runId>` since hearsay-tools/cezarion#1022, `.ai/cezar/tmp/<runId>` before it) instead of the host's values, which the least-privilege env used to forward verbatim. An exact `0` restores the host `TMPDIR` **and** skips the new pre-spawn writability check — the pre-#785 behaviour, not merely the pre-#785 environment, so a run that used to start still starts. Since #387 the per-run directory is also socket-safe: a checkout deep enough that the repo-local directory would cross the kernel's unix-socket path budget (58 bytes since hearsay-tools/cezarion#1022 — macOS's 103 usable `sun_path` bytes minus Chromium's 45-byte `org.chromium.Chromium.XXXXXX/SingletonSocket`; 78 before it) resolves it to a short `cez-agent-<12 hex>` directory under an OS temp root instead — still per-run, still probed, still reaped; repos whose path fits are untouched, byte for byte. Since #440 there are two such roots, most preferred first: the env-honouring one, and (POSIX only) the platform's own `/tmp`, consulted when the ambient `TMPDIR` itself is deep enough — routine inside a cezar task session — that its candidate crosses the budget. Removing that opt-out, weakening it to cover only the variables, or changing which spelling disables it, is breaking and takes the deprecation path below. The host `TMPDIR` is still forwarded unchanged to every process cezar spawns that is *not* an agent session.

Breaking: renaming/removing a command, flag, alias or env var; changing a default (port, workflow); changing `run` exit-code semantics. Required path: keep the old spelling as a deprecated alias for at least one minor release, print a one-line deprecation warning, document the replacement.

## 2. HTTP API of the cockpit server (`packages/cezar/src/server/server.ts`)

**Every route lives under `/api/v1`.** The unversioned `/api/*` surface was REMOVED (see the breaking entry in CHANGELOG.md): the paths below are the real URLs; the project-scoped ones also answer at `/api/v1/p/<projectId>/<path>`. A future `v2` mounts beside `v1` rather than editing these paths.

Consumed by the bundled React cockpit (`packages/cezar/web/dist`, shipped in lockstep — low risk) and by anyone scripting `localhost:4321`. Saved bookmarklets do NOT call the API — since GitHub's CSP blocked cross-origin probes they only open a page URL (`packages/web/src/lib/bookmarklet.ts`), which is why removing the unversioned surface did not break them.

What is protected now: **the shape of each route under `/api/v1`**, the three-way scope aliasing, and the SSE event vocabulary. Removing or renaming a route, or changing a response shape, is breaking exactly as before. Routes:

- Worker conversation sends accept optional `resume: true` for a parent to continue its settled worker with a new request/progress instruction. Omitted flags preserve ordinary send admission and existing retry hashes. Message receipts add optional `instruction` and `resumed`; conversation events add optional `deliveredAt`, distinct from projection `ts`. Older events remain readable. The CLI now exits 1 for `delivery: not-delivered` even though the HTTP response successfully records that rejected receipt. The stored opening continuation may carry optional `agentInputId`; its input acknowledgement and prompt retirement are atomic. Pending conversations share a bounded provider turn while retaining separate receipts and outcomes. Conversation delivery gains the value `consumed` (receipts, `conversation-message` events) with optional `consumedAt`, reported only when the recipient's harness shows the model read the message (#505); agent inputs add optional `consumedAt` and `awaitingRead`. A cockpit older than this change skips `consumed` projections it cannot parse and keeps showing the delivered one.

- Owned-worker execution identity is private `runs/<id>.identity.json` evidence, written before acceptance. Only explicit internal primitive creations carry an internal compatibility marker; service-created workers carry a concrete account binding. Intermediate owned records without valid evidence refuse launch/Continue without migration or automatic repair; inspection, stopping, verified cleanup, resources, and history remain available. Ordinary records without delegation metadata retain native account discovery.
- Owned-worker process records are private `runs/<id>.processes.json` evidence (#469), next to `<id>.identity.json`: the generation, its controlling cezar process and the agent session processes it started (`{ pid, startToken, pgid? }`, at most 32; `pgid` since hearsay-tools/cezarion#890, when the session leader leads its own process group, and destroy then signals that group). Only a dead foreign controller's generation is ever finalized from it, once every recorded process and every process working in the worktree or run scratch is gone. An absent file (a worker started before #469) is legacy evidence and relies on the working-directory scan alone; a present file that is unreadable, malformed or of another generation proves nothing, so that generation is neither finalized nor reaped. Nothing migrates it.
- Owned-worker relationships (project-scoped): `GET /api/v1/runs/:id/relationships`, including boot/default aliases. Validated run ID and empty query; bounded complete ownership lookup (up to 1,024 workers since #816, never sliced), optional parent ID, worker status/cleanup details and, for a parent, an optional additive `capacity` block (`outstanding`, `limit`, `created`, `creationLimit`), and since hearsay-tools/cezarion#864 an optional additive `titles` list (`{id, title, titleSummary?, titleOrigin?}` for the parent and every owned worker, archived ones included, absent when there are none) so the cockpit can name runs its windowed run list no longer carries, with no session credentials. The workspace runs index and `GET /api/v1/run-summaries` add an optional delegation role/wait-phase projection for both parents and workers (since #817 workers also carry `parentRunId`, and a root wait carries its worker ids and the ids of workers that reported, so lists keep their counted label), including optional request IDs to distinguish reply waits from worker-completion waits. Full records and index rows also carry optional `hasPendingHumanAsk`, derived from acknowledged question history, so a parked worker wait cannot mask human attention in lists.
- Owned-worker human cleanup (project-scoped, available even with delegation disabled): `POST /api/v1/runs/:id/worker-destroy`, strict empty body, ordinary origin/Host guard. Returns the worker destruction result (200 complete, 409 incomplete) and retains worker history and parent-collected results. Explicit child-history deletion becomes available only after verified complete cleanup and durable parent ownership/result evidence; parent history can be deleted after its child histories. Interrupted deletion remains retryable and blocks new execution. Unrelated/ordinary runs cannot be destroyed through it.
- **Owned-worker destroy retry state (hearsay-tools/cezarion#879, additive).** A worker's run record may carry an optional top-level `destroyRetry`, `{ attempts, nextAt, needsAttention? }`: how many automatic attempts ran since the last explicit destroy, when the next is due, and `needsAttention: true` once they reach the hourly cap with nothing changing. Worker inspection and the relationships route show it as `destroy.retry`. It is written only while a destroy is pending, cleared by an explicit destroy (Clean up or `cez worker destroy`) and dropped when the destroy completes. Automatic retries now back off from every minute to hourly and skip an attempt when nothing they observed has changed; no route, status code or result shape changes. Downgrade-safe: the field sits outside the strict worker `delegation`, so an older cezar strips it (and keeps it across its own writes, through the raw-record codec) instead of quarantining the worker; the stored `delegation.destroy` keeps exactly its earlier keys.
- Private delegation listener (opt-in `CEZ_DELEGATION=1`, loopback-only in the controller process, **not mounted on the cockpit or project aliases**): `POST /api/v1/delegation/discover`, `GET /api/v1/delegation/list` (parent-owned worker summaries with execution revision, settlement and cleanup state; optional receipt `offset`, at most 32 workers per page, optional `nextOffset`), `POST /api/v1/delegation/spawn`, `POST /api/v1/delegation/wait`, `POST /api/v1/delegation/cancel-wait`, `POST /api/v1/delegation/send`, `POST /api/v1/delegation/follow-up`, `POST /api/v1/delegation/reply`, `POST /api/v1/delegation/conversation`, `POST /api/v1/delegation/inbox`, `POST /api/v1/delegation/inbox/ack`, `POST /api/v1/delegation/inbox/release`, `POST /api/v1/delegation/cancel-request`, `GET /api/v1/delegation/:workerId`, `POST /api/v1/delegation/:workerId/collect`, `POST /api/v1/delegation/:workerId/steer`, `POST /api/v1/delegation/:workerId/stop`, `POST /api/v1/delegation/:workerId/destroy`, `GET /api/v1/delegation/:workerId/diff`. Every request requires its ephemeral session bearer credential and strict contract validation; caller project/run/generation are derived from credentials, never input IDs. Success shapes live in the delegation contract. Spawn accepts an additive optional `skill` to run one discovered skill, mutually exclusive with `workflow`. Workers no longer inherit the parent's selected skill (#778); legacy records keep their inline `systemPrompt`. Collection uses inspect authority and returns bounded assistant evidence, execution revision, exact status, projected outcome, proven settlement, typed availability, and a parent-owned diff snapshot reference; result files survive restart and remain separate from the run index. Failures return bounded `{code,error}` (400 invalid input/baseline, 401 unauthenticated, 403 denied scope, 409 incompatible state/capacity/diff unavailable, 503 unavailable transport); destroy returns its complete/incomplete result with exact remaining resources, using 409 for incomplete. Worker waits register immediately and carry a finite deadline plus a yield instruction. Optional `mode` supports `one` (exactly one worker), `any` (legacy default), and `all`. Settlement reasons (`outcome`, `timeout`, `cancelled`) remain, with additive `message` interruption for conversations; cancellation accepts `{waitId}` under the existing wait permission, leaves workers intact, and returns the current or last retained wait receipt. A stale ID never cancels a later wait. Discovery accepts `{kind:"runners"}` or `{kind:"models",runner}` under existing parent spawn authority, with no new durable permission. It shares host default-account catalogs with the cockpit and headless controller. Explicit default-account spawn model misses against fresh nonempty catalogs return additive `modelChoices` details (runner, requestedModel, availableModels, otherRunners) before worker allocation; inherited defaults, named-account selections, accepted retries, and unavailable/empty/stale catalogs retain their previous path. Spawn's `context.artifacts` gains an additive `{kind:"parent-file",path}` reference and `cez worker spawn` a repeatable `--attach <path>` flag (hearsay-tools/cezarion#1149): it copies a regular, git-ignored file from the parent's own worktree into the worker's worktree at the same relative path before the worker's first turn. Paths tracked at the baseline or untracked but not ignored, symlinks, `.git` components and `.gitignore` files are refused naming the path; attachments count toward the existing 32 references and 8 MiB budget and never enter the worker's diff or autosave. Downgrade: an older cezar that reads a worker record carrying a `parent-file` input fails its strict delegation schema and quarantines that worker's delegation (role `invalid`). The listener exposes no cockpit read/control routes and widens no CORS surface. Credentials never enter responses, prompts, records or events.
  - Worker inbox reserves at most 32 complete incoming messages and 100,000 text characters across the caller’s authorized conversations. A durable receipt holds the exact IDs for 120 seconds; the CLI writes the snapshot before acknowledging it. ACK marks only those inputs delivered and supports exact retries; release or expiry restores automatic delivery. Failed output attempts release, and unacknowledged IDs may replay after expiry. Receipt operations use the caller’s session generation and never reply to requests, resume settled runs, or answer human questions. Conversation inspection remains non-consuming history and adds an optional unread-message hint only for incoming unread messages included in its response.
- Static/GUI: `GET /` and every SPA shell route, `/new` (bookmarklet deep-link, query `?skill=&ref=&auto=&key=`), `/assets/:file`, `/cezarion-{lockup,mark}-{light,dark}.svg` (the themed sidebar-lockup and favicon pair, #143; it retired the single-file `/cezarion-mark.svg` the same way #142 retired `/open-mercato.svg`)
- Meta: `GET /api/v1/health` (the **only** CORS-open route — bookmarklets probe it cross-origin; its shape `{version, latestVersion, repoRoot, repo, checks, defaultRunner}` is the most externally-depended-on JSON in the app), `GET /api/v1/launch-key`
  - `repoRoot` is the absolute checkout path in local mode (the shape the saved bookmarklets read) but only the checkout's **basename** in hosted mode (`CEZ_REMOTE`), where health is CORS-open off the loopback and the absolute path would leak the developer's username (#431). Always present, always a string — but a hosted consumer must not treat it as a filesystem path.
  - Additive since the multi-project workspace (spec `.ai/specs/2026-07-20-multi-project-workspace.md`): `projects: [{id, name}]` + `bootProject` enumerate the per-user registry (section 9). **`projects[].root` is deliberately absent** — health is the CORS-open route, and a per-project absolute path would reintroduce the #431 username leak once per registered project; absolute roots live on the same-origin `GET /api/v1/projects` instead. Every pre-existing health field stays byte-identical; an unreadable registry degrades to `projects: []`, never an error.
  - Additive for issue #781: `capabilities.preview` is a new required boolean, `true` only under `CEZ_PREVIEW=1`. Every pre-existing field stays byte-identical, so a consumer that ignores the key sees no change; it is what the cockpit's preview toggle and server-card actions read. An older server omits it, which the cockpit treats as off.
  - Additive for voice mode (spec `.ai/specs/2026-10-21-voice-mode.md`): `capabilities.voice` is a new required boolean, `true` only when `CEZ_VOICE=1` and `TYPESAFE_API_KEY` is non-empty (or `CEZ_DRY_RUN=1`). Every pre-existing field stays byte-identical, so a consumer that ignores the key sees no change; it is what the cockpit's ⌘K sentence input reads. An older server omits it, which the cockpit treats as off.
  - Additive for issue #737: `capabilities.tokenUsageMetrics` and `capabilities.costMetrics` independently control raw input/output token and reported-cost presentation. Current servers always send both booleans; newer clients fall back to the legacy `tokenMetrics` value (and then visible) for older servers. `tokenMetrics` remains as the fail-closed combined value `tokenUsageMetrics && costMetrics`, so an older cockpit never reveals a dimension a deployment hid. All three flags are presentation-only — run and event telemetry remain unchanged.
- Workspace: `GET/POST /api/v1/projects`, `PATCH /api/v1/projects/:projectId`, `DELETE /api/v1/projects/:projectId`, `POST /api/v1/projects/:projectId/webhook/test`, `POST /api/v1/projects/:projectId/webhooks`, `PATCH/DELETE /api/v1/projects/:projectId/webhooks/:webhookId`, `POST /api/v1/projects/:projectId/webhooks/:webhookId/test`, `POST /api/v1/projects/checkout`, `POST /api/v1/projects/create`, `GET /api/v1/projects/github-owners`, `GET /api/v1/fs/browse`, `GET /api/v1/models`, `GET /api/v1/providers/status`, `POST /api/v1/providers/connect`, `PUT /api/v1/providers/:provider/enabled`, `POST /api/v1/providers/:provider/retry` — the registered-project, filesystem, host model-catalog, and provider-authentication surface. The projects GET shape is `{projects: [{id, name, root, branch?, status, source, lastOpenedAt, forge?, maxParallel?}], bootProject, projectsDir}` (`status`: `ok`/`missing`/`not-git`; `branch` only when cheaply readable; `forge?` is the additive per-project forge classification (#698) — `'github'` when the root's remote parses to a known forge host, omitted otherwise, so an old consumer that ignores it sees no change; `maxParallel?` is the additive per-project concurrency cap from spec `.ai/specs/2026-07-22-per-project-concurrency.md` — omitted means "inherit the workspace cap", so an old consumer that ignores it sees no change; `repoUrl?` is the additive, credential-free web root of the project's remote (`https://github.com/owner/repo`, rebuilt from the PARSED remote so a token in it can never reach a client), which is what lets a cross-project surface link a reference the run knows only by number; `tags?` is the additive grouping-label list the global Tasks page filters and groups by — normalized (trimmed, deduped case-insensitively, sorted) and **omitted rather than `[]`** for an untagged project, so an old consumer that ignores it sees no change). `PATCH /api/v1/projects/:projectId` is additive and **per-key**: body `{maxParallel?: 1..16 | null, tags?: string[] | null}`, each field applied ONLY when the body names it (`webhook?: {url, token?} | null`, #589, is the third such key: an omitted `token` keeps the stored one, `''` clears it, `null` removes the webhook, and no response ever carries the token — entries answer `webhook?: {url, tokenSet, triggers?}`; `triggers?` (hearsay-tools/cezarion#1356, additive) is the stored state selection, accepted as `webhook.triggers` on the PATCH, omitted when none is stored, with an omitted `triggers` keeping the stored list as an omitted token does), so the pre-tags `{maxParallel}` body still means exactly what it always did and a tags-only body cannot clear a concurrency ceiling. `null` clears either (an empty `tags` array clears too); an empty body is refused with a 400, as it always was. The answer is `{project}` in the same entry shape. **The agent-account selection is deliberately NOT here** — it lives in `~/.cezar/agent-accounts.json` and is written through `PUT /api/v1/workspace/agent-profiles/selection`, so this route and the project registry are untouched by that feature. Same-origin only — no CORS, which is exactly what licenses the absolute `root`s that health must never carry. The list never 404s: an empty or unreadable registry answers `projects: []`.

They are replaced by `waits`, `lastWaits` and `lastWaitsError`. `waits` holds the run's open and recently resolved waits, at most 16 open. Each entry is `{ id, kind, source, via, registeredAt, deadline, phase, turnId, resolvedAt?, deliveredAt?, cancelledAt? }`, with `phase` one of `open`, `resolved`, `delivered` or `cancelled`. A `kind: 'ci'` entry also carries what `ciWait` carried: the PR identity, `headSha`, `generation`, `timeoutSeconds` and, once observed, `result`. A `kind: 'timer'` entry carries `seconds` (60–7,200) and an optional `note`. `lastWaits` holds settled waits, newest last, at most 16. `lastWaitsError` is the retained recovery message that `lastCiWaitError` was. To migrate, read the `kind: 'ci'` entries of `waits` instead of `ciWait`, and a `kind: 'timer'` entry's `deadline` instead of `monitoringWakeAt`. `monitoringWakeCapReached` has no replacement: once the automatic-wake budget is spent, `cezar_wait` refuses a new timer with `wake_budget_spent`, so the agent learns it from the tool's answer.     - **A failed run can keep its waits.** A session that keeps failing, or closing cleanly, while the run owes resolved results (or, since hearsay-tools/cezarion#1301, a queued completion refusal, which the failed run keeps undelivered for Continue; that input carries the optional `purpose: 'completion-refusal'`, absent from every other `AgentInput`) stops after 3 consecutive failed delivery attempts and settles the run `failed` with the note `could not deliver wait results after 3 attempts — continue this task to retry`. A request with none of them is the first page, exactly as before, and `limit` keeps its meaning (capped server-side; one GraphQL request asks for at most 100 rows). Additive response fields: `issuesTotal`/`prsTotal` (GitHub's exact open totals) and `issuesNextCursor`/`prsNextCursor` (the cursor for the next page, `null` once that side is exhausted; absent means a server that does not page, so a client must not read a missing cursor as "more to come"). Each side pages on its own cursor, so an exhausted side is never restarted. `commentsDeferred: true` (additive) says the rows' `comments` are a placeholder `0`, the same value the list has always shipped when counts could not be read; the real numbers come from `/github/comment-counts`. **`body` on list rows is deprecated**: it is still sent, unchanged, and is removed in a later minor; read an item's body from the comments route's `detail`. Breaking: removing `body` before that minor, making a cursor non-opaque, or answering `issuesNextCursor: null` for a side that has more rows.
  - `GET /api/v1/github/comment-counts?kind=issue|pr&numbers=<csv>[&refresh=1]` (hearsay-tools/cezarion#1183) is additive: the comment counts the paged list defers. `numbers` is a comma-separated list of positive integers without leading zeros, capped at 100 (`GITHUB_COMMENT_COUNTS_MAX`); a malformed list, a missing `kind` or a `refresh` other than `1` is a `400 {error}`. The response is `{available: true, counts}` (a `number → count` map) or `{available: false, reason}`, degrading exactly like `/github/checks` and never a 5xx. A number GitHub does not know is absent from `counts`, never `0`. Answers are cached per repository and number; `refresh=1` bypasses that cache. Breaking: answering `0` for an unknown number, or removing the route while the list still sets `commentsDeferred`.
  - `GET /api/v1/github/search?kind=issue|pr&q=<text>&limit=<n>` (#730) is additive: the list call (`GET /api/v1/github`) returns the **open** set only — `gh issue list` / `gh pr list` default to `--state open` — so the tab's in-memory filter structurally cannot match a closed or merged item, and this endpoint is the cross-state lookup it falls back to. `kind` and a 1–256-char `q` are required, `limit` is optional and capped at `GH_SEARCH_MAX` (50); anything malformed is a `400 {error}`. The response is `{available, items, truncated?, labelColors?}` — `items` are the same `githubItemSchema` rows the list ships, with `checks` always `null` (hydrated lazily through `/api/v1/github/checks` like list rows) — or `{available: false, reason}`, degrading exactly like the list and never a 5xx. `GET /api/v1/github`'s response shape is untouched.
  - `GET /api/v1/github/ref-status?prs=<csv>&issues=<csv>` is additive and is the batched read behind a task's PR/issue chip (one request per project for a whole table, not one per chip). Both query keys are optional and at least one must name something (400 otherwise); each is a comma-separated list of positive numbers capped at 100 (400 on a malformed list). The response is `{available: true, prs, issues, conflicts?, recheckAfterMs}` — two `number → status` maps plus the cadence — or `{available: false, reason, recheckAfterMs}`, degrading in the payload exactly like `/github/checks`, never a 5xx. `recheckAfterMs` is how long the answer holds (milliseconds), or `null` for "nothing in this answer can change; do not schedule anything": the SERVER owns that judgement, because whether a status can still move is forge semantics and lives next to the cache that decides whether asking would even reach GitHub. A client is expected to obey it rather than keep its own table. A number the forge does not know is **absent** from its map rather than present with a fallback: absent means "nothing is known", which the cockpit paints as the neutral chip it painted before statuses existed, and collapsing that into a status would let "we could not ask" render as "nothing is wrong". The status vocabulary is `draft | review-required | changes-requested | checks-pending | checks-failing | ready | merged | closed` for PRs and `open | completed | not-planned` for issues; adding a value is additive (an unknown one renders neutral), renaming or removing one is breaking. `conflicts` is an **optional additive** list of the PR numbers the forge reports as `CONFLICTING` — a second axis, never folded into the status, because a pull request can be `ready` (open, green, nobody waited on) and unmergeable at the same time and one word cannot say both. It rides the same GraphQL node the statuses come from, so it costs no extra request, and it names OPEN pull requests only. Its **absence means "nothing is known about mergeability"** — an older server omits the key entirely, and GitHub's own still-computing `UNKNOWN` is never listed — so a client must not read a missing number as "merges cleanly"; the cockpit paints the conflict chip on `true` alone. Removing the key, or letting it mean "no conflicts", is breaking. GitHub computes mergeability on demand and answers `UNKNOWN` while it does, so a batch holding such a reference comes back with a **much shorter `recheckAfterMs` (seconds, not the usual minute)** for as long as that is plausibly still being computed — the one existing knob, used as designed: a client obeys the cadence rather than keeping its own, and the server never caches a non-answer for as long as an answer.
- **Content negotiation on the two mixed-format routes — additive, and the query flags stay the wire.** `GET /api/v1/repo/commit/:sha` serves the legacy `text/plain` blob or the structured `{sha, subject, author, when, files, stat}` payload; `GET /api/v1/runs/:id/files` serves the JSON listing/metadata or an image file's raw BYTES. Both now also read the request's `Accept` header, under a fixed precedence: **(1) the query flag whenever the request carries it** (`?structured=`, `?raw=` — present-but-not-`1` is an explicit opt-out, so a header can never override a caller that said what it wanted in the URL), **(2) otherwise the best `Accept` match**, **(3) otherwise the route's established default** — the text blob for `/repo/commit/:sha`, the JSON listing for `/runs/:id/files`. `*/*` matches nothing, deliberately: it is what `fetch`, `curl` and XHR send when they have no preference, so **every existing caller's answer is byte-identical**. Both routes answer `Vary: Accept`, and each response carries the `Content-Type` of what it actually sent. The one behavioural addition is that a client whose `Accept` really does ask for the other representation now gets it — e.g. an `<img>` or a browser navigation to a worktree image receives the bytes, with the same allowlist, size cap, `nosniff` and sandbox CSP the `raw=1` path has always applied. A negotiated (as opposed to flag-driven) image preference that the resource cannot satisfy falls back to the JSON representation rather than 409ing; `?raw=1` keeps its 409 and its exact wording. Breaking: changing that precedence, making `*/*` select a non-default representation, or letting `Accept` override a present query flag.
- Agent config (spec open-mercato/cezar#404, additive): `GET /api/v1/agent-config`, `GET/PUT /api/v1/agent-config/:id` — writes 409 in hosted mode (`CEZ_REMOTE`) by design; the `format` enum gained `yaml` for OMP's `config.yml` (additive: existing entries keep their format)
- SSE event names: `run-event` (v1), `ui-event` (v2 dotted types), `provider-status` (workspace-only host provider row)

**Project-scoped mirror — `/api/v1/p/:projectId/*`** (multi-project workspace, Phase 2): every per-project route above is registered **once** and mounted **twice**, unscoped `/api/v1/<path>` and scoped `/api/v1/p/:projectId/<path>`, sharing one handler so the spellings cannot drift. The contract:

- The unscoped routes stay bound to the **boot project** (the repo `cez serve` started in) and answer **byte-identically** to `/api/v1/p/<bootId>/<path>` and `/api/v1/p/default/<path>`. That three-way parity IS the protected surface — enforced by `packages/cezar/src/server/route-parity.test.ts`, which iterates a manifest derived from the app's actual route registrations (so a newly added scoped route is parity-tested automatically, and the suite can never drift from the code).
- `projectId` is validated at the route boundary before any registry or filesystem touch: the slug shape (`^[a-z0-9][a-z0-9-]{0,63}$`) or the reserved literal `default`, which always aliases the boot project. Unknown or malformed id → `404 {error}`; a registered project whose folder is gone → `409 {error}`. Both status/shape pairs are part of the contract.
- Non-boot projects build lazily on first scoped touch (own store, own launch key, same crash recovery the boot project gets); nothing about the boot project's observable behavior changed with the mirror.
- Workspace-level routes (`/api/v1/health`, `/api/v1/projects`, `/api/v1/providers/*`, `/api/v1/workspace/*`) are single-mount and **never** mirrored under `/api/v1/p/` — they answer for the whole workspace, so a scoped spelling would be a second surface to protect with no consumer.

**One surface, versioned — `/api/v1/*`** (spec `.ai/specs/2026-07-23-independent-server-web-packages.md`):

- **Why it exists.** Hono infers an API's types only from routes registered through a *chained* builder. Every family is chained and mounted into one versioned table, which is what makes `AppType` (`packages/cezar/src/server/app-type.ts`) — and the client `@open-mercato/cezar-api-client` builds from it — cover the whole API rather than a hand-written mirror of it.
- **No unversioned twin.** `versioned-surface.test.ts` fails if any route appears outside `/api/v1`. A route added as a loose `app.get('/api/x')` would answer while being invisible to the typed client, which is the two-surface problem this removed.
- **Version, then project.** The version is the outer dimension (`/api/v1/p/:projectId/…`): a consumer picks its API version once and addresses projects inside it.
- **Transcript compatibility.** Run transcripts persist absolute image URLs and keep them forever, so NDJSON written by older versions still names the unversioned `/api/runs/<id>/images/…`. The cockpit upgrades those onto `/api/v1` at render time (`resolveApiUrl`); the stored bytes are never rewritten.

**Cockpit page URLs — `/p/:projectId/*`** (multi-project workspace, Phase 3): every cockpit *page* now lives under a project prefix too (`packages/web/src/routes.tsx`), mounted by one `ProjectScopeRoute` layout gate. Unlike the API mirror above there is no unprefixed page spelling left to answer — the flat URLs redirect instead, and that redirect is a protected surface in its own right because it is what saved bookmarks and bookmarklets land on:

- **Legacy flat → `/p/<boot>/…` is permanent.** Every pre-multi-project path (`/`, `/new`, `/tasks/:id`, `/settings/*`, …) redirects to the boot project's scoped twin preserving **path, query and hash byte-for-byte**. It is a client-side `replace` navigation, not an HTTP 3xx — the server already serves `index.html` for every non-`/api`, non-asset GET (`packages/cezar/src/server/static-ui.ts`), so a **cold load** at a flat URL lands exactly as `open()` from github.com performs it. Until `/api/v1/health` names the boot project the router shows a quiet resolving state, never a flashed wrong screen. One refinement (hearsay-tools/cezarion#925): a flat **task link** (`/tasks/<run-id>/…`) names a run, and a run belongs to the project whose store holds it — so that one shape resolves its **owner** from the cross-project runs index (`GET /api/v1/workspace/runs-index`) and redirects there, keeping path/query/hash byte-for-byte. A run the loaded index does not know (the index is a capped window), an index that cannot answer, or a run owned by the boot project itself lands on the boot project exactly as before — no flat URL changed where it lands for anything the boot project could serve.
- **Thread file/artifact deep links stamp the task's owning project** (hearsay-tools/cezarion#925): the cockpit's markdown rewrite (`TaskFileScope` → `taskFileHref`) prefixes `/p/<projectId>/tasks/<runId>/files?…` with the project whose **route matched** — the only store that can be serving the rendered run — never the ambient viewer scope or a silent boot fallback. `cez artifact publish` discovers the same owner from artifact storage and the workspace registry with a realpath-symmetric match (an OS-aliased spelling still names its owner; an owner absent from the registry retains the legacy flat link, which the owner-resolving redirect above then lands correctly).
- **`/p/default/…` is the page-level twin of the API's `default` alias** — the reserved literal, never an allocated slug, normalized to the real boot slug with a `replace` navigation so the address bar always names the project; the remaining path, query and hash survive byte-for-byte. An id the registry doesn't know renders the "not registered here" screen — the cockpit twin of the API's `404`.
- **The redirect IS the bookmarklet contract.** A generated launcher is now `<origin>/p/<projectId>/new?skill=&auto=&key=&ref=` (`packages/web/src/lib/bookmarklet.ts`): **only the path gained a prefix**, the query grammar after `?` is byte-identical, and `key` is that project's own `.ai/cezar/launch-key` (each repo keeps its own — the scoped API client fetches the right one). Generating without a project id still emits the exact legacy flat `/new?…`. Every bookmarklet already saved in somebody's bar predates the prefix, so **the legacy redirect is the only thing keeping it working** — deleting it breaks browsers this repo cannot reach, which is why it is listed as permanent and not as a deprecation window.
- **Settings split, old URLs kept** (`packages/web/src/routes/settings/registry.tsx`): project sections live at `/p/<id>/settings/<section>` (agents, worktrees, bookmarklets, prompt templates), global ones at `/settings/global/<section>` — the one cockpit area deliberately **outside** every project scope, because appearance and notifications are the user's, resources are the machine's, and the Projects pane *is* the registry. A section that moved keeps **both** old spellings landing: `/p/<id>/settings/<global-id>` redirects to the global twin, and the legacy flat `/settings/<global-id>` reaches it through the flat redirect first. The **store** moved with them — appearance and notifications now write `~/.cezar/ui-state.json` via `/api/v1/workspace/ui-state`, resources writes `/api/v1/workspace/config`, and the project sections stay on the per-repo `/api/v1/config` + `/api/v1/ui-state` (section 3). Migration 001 copied the pre-existing per-repo `appearance`/`notifications` values up (section 9), so the split is invisible on upgrade and a downgraded cezar still reads its local copies.

Breaking: removing/renaming a route; making a previously optional body field required; removing a response field; changing an SSE event name (`run`, `run-event`, `run-deleted`, `usage`, `ping` — or, on the workspace stream, `project-added`, `project-removed`, `checkout-progress`, `provider-status`, `project-ready`) or the `seq` dedup contract; breaking the three-way alias parity (an unscoped `/api/v1/*` answer diverging in status, content type or body from its `/api/v1/p/<boot>`/`/api/v1/p/default` spellings); changing the scoped 404/409 project-resolution contract or the meaning of the `default` alias; stamping or widening the boot-project `/api/v1/events` stream; narrowing `/api/v1/health` CORS or its fields; changing `/new` query parameters (breaks saved bookmarklets); **dropping the legacy-flat → `/p/<boot>` page redirect** — or letting it lose the query/hash, which is the same break one step quieter; changing the meaning of the `default` page alias; moving a settings section without leaving its old URL redirecting to the new one. Required path: additive first; if removal is unavoidable, keep the old route/field answering for one minor release and note it in the CHANGELOG. `/new` deserves extra caution — it lives in users' browsers (saved bookmarklets), not in this repo.

- **Run-store 409s (hearsay-tools/cezarion#779, additive error status).** Two new reasons for an existing `409 { error }` body; no 200 shape changes and no route is added. `error` is a human sentence, never a code to branch on. (1) *Another process owns the run.* When `serve` and a headless `cez run` (or two cockpits) open one project, each process writes only the runs it owns. A control on a run that another live process owns answers 409 `{ error }` and changes nothing; reads are never refused, and a run whose owner died is adopted first (its live runs are settled as interrupted, never resumed; only Continue resumes) and the control then applies. Stop on such a run settles it as cancelled instead and answers `{ cancelled: true }`. This is a new answer on `POST /runs/:id/archive`, `/pin`, `/notify`, `/read`, `/unread`, `/cancel` and `DELETE /runs/:id/auto-resume`, and on the routes that already had a 409: `PATCH /runs/:id`, `POST /runs/:id/messages`, `PATCH` and `DELETE /runs/:id/queued-messages/:msgId`, `POST /runs/:id/finish`, `/continue`, `/open-in-cli`, `/open-in`, `/git/commit`, `/git/push`, `/pr`, `/remove-worktree`, `DELETE /runs/:id`, and `POST /runs/:id/worker-destroy` (which keeps its `{ code: 'incompatible_state', error }` delegation shape). Every one has its project alias. (2) *The project's run store cannot open.* Every project route of that project answers 409 `{ error }` naming the cause (kinds and fixes in section 3, "When the run store cannot open"), under `/api/v1/<path>`, `/api/v1/p/<boot>/<path>` and `/api/v1/p/default/<path>`. Workspace routes (`/health`, `/projects`, …) and other projects keep answering. A project opened lazily retries on the next request; the boot project needs a restart of cezar. A client that already handles 409 on these routes needs no change; one that treated every non-409 failure as retryable must not retry this one blindly.

### Private CI tool IPC (#474)

`GET /api/v1/tools/ci-wait` (and, until hearsay-tools/cezarion#1236, its `POST`) belong to a separate, chained, typed Hono family on
local IPC (Unix-domain socket / Windows named pipe), not the cockpit server's
route table. It has no `/p/:projectId` alias and must never become an unauthenticated
network route. Middleware validates the strict shared `CiWaitRequest`; a
memory-only capability determines project, run and session generation. No caller
run ID or path is accepted. `CEZ_TOOL_TOKEN` / `CEZ_TOOL_SOCKET` are internal
provisioned environment values, not authored configuration or delegation grants.
The MCP tool name `cezar_wait_for_ci` and its default 1,800-second timeout (range
1–7,200) were model-facing compatibility surfaces, deprecated since
hearsay-tools/cezarion#1233 and removed in hearsay-tools/cezarion#1236 (see below). Preserve user MCP configuration
and explicit denials when provisioning a session.

Additive for #781 (live preview v1): `POST /api/v1/tools/preview-serve` joins the same
private family, behind the same bearer capability and a 16 KiB body limit. Every answer
except a missing or revoked capability (`401`) is `200` with the shared
`PreviewServeResult` `{ ok, code, message, hint }`, so an agent can repair a bad call from
the hint: `invalid_input` names the first failing field and gives a valid example call,
`preview_disabled` answers whenever `CEZ_PREVIEW` is not exactly `1`, and `headless` answers
when the session carries no preview registration. The MCP tool `cezar_preview_serve` is
listed, and admitted on every runner, only under `CEZ_PREVIEW=1`, which the provisioned
session environment carries to the adapter. `cezar_wait_for_ci` and its route are unchanged.

Additive for #803: `POST /api/v1/tools/preview-stop` uses that same private capability,
16 KiB limit and exact opt-in. Its Zod request is `{ port, restart?: boolean }`; extra
fields (including run identity or a command) are rejected. `PreviewStopResult` uses
`{ ok, code, message, hint }` with the same 200/401 convention. The adjacent MCP tool
`cezar_preview_stop` controls only this run's Cezar-started servers. Restart reuses an
unchanged owner-approved command after stop or crash; command, cwd or path changes
invalidate approval and require Run and open again. Adopted/other-run servers and
ports occupied after teardown are refused with recovery hints. Approval is local to
the running host, not persisted across cockpit restarts.

Additive for hearsay-tools/cezarion#1233 (unified waits, phase 1): `POST /api/v1/tools/wait`
and `POST /api/v1/tools/cancel-wait` join the same private family, behind the same bearer
capability and a 16 KiB body limit. Middleware validates the strict shared
`CezarWaitRequest` (`{ kind: 'ci', pr, timeout_seconds? }`, `kind: 'pr'` since hearsay-tools/cezarion#1425, or
`{ kind: 'timer', seconds, note? }`) and `CezarCancelWaitRequest` (`{ wait_id }`). Every
answer except a missing or revoked capability (`401`) is `200` with the typed
`CezarWaitAnswer` (`{ ok: true, wait_id, kind, deadline, open_waits }` or
`{ ok: false, code, message, open_waits? }`) or `CezarCancelWaitAnswer`
(`{ cancelled: true, wait_id, open_waits }` or `{ cancelled: false, code, message, open_waits? }`,
where `already_resolved` means the result still arrives with the next wake). The MCP tools
`cezar_wait` and `cezar_cancel_wait` are listed and admitted on every runner. `cezar_wait`
advertises one flat `type: 'object'` input schema with a `kind` enum, because the Anthropic
tool API refuses a top-level `oneOf`/`anyOf`/`allOf`; the union is checked only on the
server. Their names, the `kind` values, the timer range (60–7,200 seconds, `note` up to 512
characters) and the CI timeout default and range are model-facing compatibility surfaces.

**Deprecated (hearsay-tools/cezarion#1233):** `cezar_wait_for_ci` and
`GET`/`POST /api/v1/tools/ci-wait` kept working with an unchanged receipt, and a
registration through them opened a `ci` entry in the same wait list. The tool's description
pointed to `cezar_wait`, and the server instructions no longer suggested it.

**Breaking, phase 4b (hearsay-tools/cezarion#1236):** the MCP tool `cezar_wait_for_ci` and
`POST /api/v1/tools/ci-wait` are removed. No runner lists or admits the tool; a call to it is
an unknown tool, and the POST answers 404. Migration: call `cezar_wait` with `kind: "ci"`
(the same `pr` and `timeout_seconds`, with the same bounds and default). The answer shape
differs: the removed tool answered the `CiWaitReceipt` (`{ waitId, prUrl, repository,
prNumber, headSha, registeredAt, deadline, phase }`, refusals as `{ code, message }` with

deadline, open_waits }` or `{ ok: false, code, message, open_waits? }`, always `200`). The
authenticated `GET /api/v1/tools/ci-wait` stays: it holds the adapter's lifetime connection,
and its path is historical. Stored wait entries with `via: 'cezar_wait_for_ci'` still parse.

**Breaking (hearsay-tools/cezarion#1425):** `cezar_wait`'s `kind: "ci"` is replaced by
`kind: "pr"`, with no alias. A request with `kind: "ci"` answers `invalid_request`, and its
message names `kind "pr"`. The `pr` kind takes the same `pr` and `timeout_seconds` (same bounds
and default) plus `until` (`"checks"`, the default, or `"merge"`) and `wake_on_conflict` (boolean,
default `true`). The answer's `kind` and every `open_waits[].kind` read `pr`. Migration: send
`kind: "pr"`; a request with no `until` waits for checks as `kind: "ci"` did.

Additive for hearsay-tools/cezarion#1446: `CezarWaitRequest` adds the arm
`{ kind: "process", pid, exit_file?, timeout_seconds?, note? }` (`pid` an integer of at least 2,
`exit_file` at most 4,096 characters, `timeout_seconds` 1–7,200 with default 1,800). The flat
tool schema adds `pid` and `exit_file`, and its `kind` enum adds `process`. `CezarWaitAnswer`
refusals add three codes: `exit_file_outside` (the exit file is outside the task worktree and
the task temp directory), `process_not_allowed` (Cezar's own process or an agent session
leader) and `process_not_owned` (the process belongs to another user). A process wait also
answers `timers_disabled` and `wake_budget_spent`, as a timer does. Each `open_waits`
entry's `kind` gains `process`.

Additive for hearsay-tools/cezarion#1234 (unified waits, phase 2): `POST /api/v1/tools/ask` joins
the private family, behind the same bearer capability and a 16 KiB body limit. Middleware
validates the strict `CezarAskRequest` (`{ questions }`, the ask card: 1–4 questions, each with a
header of at most 12 characters, the question, and 2–4 options or none for an open question).
Every answer except a missing or revoked capability (`401`) is `200` with the typed
`CezarAskAnswer`: `{ ok: true, wait_id, open_waits }` or `{ ok: false, code, message, open_waits? }`,
where `code` includes `autonomous_run`. `CezarWaitRequest` and `CezarWaitAnswer` are unchanged:
`cezar_wait` refuses `kind: "human"` with `invalid_request`, and its message names `cezar_ask`.
Each `open_waits` entry's `kind` gains `human`, which carries no `deadline`, and
`CezarCancelWaitAnswer` refusals gain `human_question` (the user already saw the question).
The ask format (`askQuestionSchema`) makes `options` optional: a question without them is open,
and the user answers it in words. The ask line, the `ask.requested` event, a native-ask card and a
worker question routed to its parent may therefore carry a question without `options`; a question
with options keeps the 2–4 bound. `POST /api/v1/tools/done` joins the same private family, behind the same bearer capability and
a 16 KiB body limit. Middleware validates the strict `CezarDoneRequest` (`{ summary? }`, at
most 2,000 characters). Every answer except a missing or revoked capability (`401`) is `200`
with the typed `CezarDoneAnswer`: `{ ok: true, finishes: 'at_turn_end', completes, open_waits }`
or `{ ok: false, code, message, workers?, open_waits? }`. `completes` is `task`, or `step` with
`next_step` naming the next workflow step (hearsay-tools/cezarion#1620). `code` keeps
`not_final_step` in its enum for old clients, but no answer returns it since
hearsay-tools/cezarion#1620. `workers` lists up to 64
`{ worker_id, reason }` with `reason` one of `outstanding`, `uncollected` or `question`. The MCP
tools `cezar_ask` and `cezar_done` are listed and admitted on every runner. Their names,
`cezar_ask`'s card bounds (open questions included) and `cezar_done`'s `summary` bound are
model-facing compatibility surfaces. A session with cezar
tools is taught these tools in place of the `CEZ:DONE`, `CEZ:MONITORING` and ask-marker lines;
the lines keep working as aliases that open the same waits and close through the same path.

- Task file links and published output (#418, additive): `GET /api/v1/runs/:id/file-link`, `GET /api/v1/runs/:id/artifacts`, `GET /api/v1/runs/:id/artifacts/:artifactId`, `GET /api/v1/runs/:id/artifacts/:artifactId/download`, `GET /api/v1/runs/:id/artifacts/:artifactId/image`. ## 3. `.ai/cezar/` state files (`packages/cezar/src/runs/store.ts` and friends)

Written by one version, read by the next, and hand-editable by design:

- **`runs.db`** (hearsay-tools/cezarion#779) — the run store: a SQLite database (`node:sqlite`, WAL), one per project, authoritative for run state from the first start that imports `runs.json`. One row per run: `data` is the complete `RunRecord` JSON (zod schema in `packages/cezar/src/runs/store.ts`), `summary` is its `RunSummary` JSON, and a few more columns are copies of record fields kept for queries. ### Moving run state from `runs.json` to `runs.db` (hearsay-tools/cezarion#779)

This is the one deliberate exception to "run state never migrates" (section 9). It is bounded:

- **One import, additive.** The first start of a project without a completed import reads `runs.json`, saves its exact bytes as `runs.json.pre-sqlite.bak`, and writes every record plus a completion marker in one transaction. A record in `runs.json` that does not parse is skipped and every other record is imported; a `runs.json` that does not parse at all (not JSON, or not an array) imports as an empty history. Either way the import prints one warning that names how many runs it skipped and the backup that keeps the exact bytes. The marker is still written, `runs.json` is never read again, and its bytes stay in `runs.json` and the backup. To import the skipped runs after all, repair `runs.json`, move `runs.db`, `runs.db-wal` and `runs.db-shm` aside (step 3.1), skip step 3.2, which would copy the unrepaired backup over your repair, and start cezar. Like step 3, this drops runs made since the import from the list; to get them back later, keep the moved set and use step 4 on it. The first backup keeps the unrepaired bytes, and the repaired bytes are saved beside it as `runs.json.pre-sqlite.<hash>.bak`. A crash or a refusal commits nothing, so the next start imports again from the beginning. Once the marker exists, `runs.db` is authoritative. An empty project gets an empty database with the marker set.
- **Policy: no dual-write, a downgrade sees migration-time history, a re-upgrade never imports divergent legacy writes automatically.** Verbatim from the approved design: "Keep `runs.json` for older versions, with no dual-write: downgrade sees migration-time history, and re-upgrade never imports divergent legacy writes automatically." In practice:
  - An older cezar started after the upgrade reads `runs.json` as it was at the import. It does not see runs made since, and what it writes goes only to `runs.json`.
  - A newer cezar started again ignores `runs.json`. Runs the older cezar made or changed in between are not in `runs.db`. They are not lost: they stay in `runs.json`, and the section below merges them by hand.
  - Per-run NDJSON logs, handoff files and images under `runs/` are shared by every version and are untouched by the move.
- **Stop older cezar before upgrading.** The import refuses to run while a live older cockpit is serving the project (it names the pid and URL) or while `runs.json` changes during the import. Some older writers hold no lock: `serve` up to 0.15.0 and any older `cez run`. One of those that saves nothing during the import window (milliseconds up to about 1.2 s) cannot be seen, and whatever it writes later is a divergent legacy write that is never imported. Stop every cezar process of the project, upgrade, start the new one.
- **Node 24.21.0 or newer** is supported (section 6). The SQLite migration originally required 24.15, the first release where `node:sqlite` is a release candidate (stability 1.2). The minimum is now 24.21.0; CI builds and tests the packaged CLI on exactly that version. `node:sqlite` loads unflagged from Node 22.13, but cezar has no startup version check and npm only warns about `engines`, so an older Node may start outside the supported range; before 22.13 cezar fails at start.
- **Corrupt, busy, unreadable or newer files are never repaired automatically.** A damaged `runs.db`, `-wal` and `-shm` stay where they are, and cezar never restores a stale `runs.json` over them or starts empty. The project answers with the cause instead (table below).

#### Recovering run history

Every step needs every cezar process of the project stopped: `serve`, a headless `cez run`, and anything started with `npx cezarion`. Run the commands in the project root. Move files, never delete them, until you have checked the result.

1. **Back up `runs.db`.** Copy `.ai/cezar/runs.db`, `runs.db-wal` and `runs.db-shm` together (a file that does not exist is fine). After a clean stop the last two are usually gone and `runs.db` alone is complete. A copy of `runs.db` taken while cezar runs, without its `-wal`, is not a backup.
2. **Restore a backup.** Move the current `runs.db`, `runs.db-wal` and `runs.db-shm` aside, copy the backed-up set into `.ai/cezar/`, start cezar. Never mix a `runs.db` with another copy's `-wal`.
3. **Rebuild from `runs.json.pre-sqlite.bak`** (the rebuild a damaged-database message names when it says to "rebuild them from runs.json.pre-sqlite.bak" as this section describes). This returns the project to the history it had at the import and drops every run made since from the list. Their `runs/<id>.*` files stay on disk, and no run lists them.
   1. Move `runs.db`, `runs.db-wal` and `runs.db-shm` aside. If you want the newer runs back later, keep the set and use step 4 on it.
   2. Move `.ai/cezar/runs.json` aside, then copy `.ai/cezar/runs.json.pre-sqlite.bak` to `.ai/cezar/runs.json`. Moving only the database makes the next start import whatever `runs.json` holds, which may be a file an older cezar changed.
   3. Start cezar. It imports the file once and writes a fresh `runs.db`.
4. **Export `runs.db` as `runs.json`** (read the new history, or hand it to an older cezar). With Node 24.21.0 or newer:

   ```bash
   node --input-type=module -e "import { DatabaseSync } from 'node:sqlite'; import { writeFileSync } from 'node:fs'; const db = new DatabaseSync('.ai/cezar/runs.db', { readOnly: true }); const rows = db.prepare('SELECT data FROM runs ORDER BY created_at, id').all(); writeFileSync('runs.export.json', '[' + rows.map((row) => row.data).join(',') + ']'); console.log(rows.length + ' runs')"
   ```

   `runs.export.json` is the same array of `RunRecord` that `runs.json` always was. To downgrade with the new history, move the current `runs.json` aside and put the export in its place as `.ai/cezar/runs.json`, then start the older cezar. Leave `runs.db` where it is: the older cezar does not read it.
5. **Re-upgrade after a downgrade, keeping both histories.** Export as in step 4, then merge by run id. This example keeps the `runs.db` copy when both files hold the same id, so choose the order for your case:

   ```bash
   jq -s 'add | group_by(.id) | map(last)' .ai/cezar/runs.json runs.export.json > runs.merged.json
   ```

   Move `runs.db`, `runs.db-wal` and `runs.db-shm` aside, put `runs.merged.json` in place as `.ai/cezar/runs.json`, start cezar. It imports the merged file once. The first backup no longer matches those bytes, so they are saved as `runs.json.pre-sqlite.<hash>.bak` beside it.

#### When the run store cannot open

`RunStore.open` never returns an empty store. The cockpit shows the message as the project's 409 `{ error }` and the CLI prints it on stderr (`cez run` exits 1 and writes nothing). Restarting cezar is always correct; a lazily opened project also retries on its next request, so a reload is enough once the cause is gone.

| Kind | Cause | What to do |
| --- | --- | --- |
| `corrupt` | `runs.db` is not a SQLite file, or SQLite reports a damaged page | cezar leaves the three files in place and never modifies the database or its `-wal`. Restore a backup (step 2) or rebuild from `runs.json.pre-sqlite.bak` (step 3), then restart. |
| `busy` | Another cezar process held the write lock beyond about 3.5 s at boot, or longer than one attempt on a lazy open | Wait for the other process to finish or stop it, then restart. |
| `permission` | The data directory, `runs.db` or the backup cannot be read or written | Give your user read and write access to `.ai/cezar/`, then restart. |
| `disk-full` | No space for `runs.db` or the backup | Free disk space, then restart. |
| `unsupported-schema` | `runs.db` was written by a newer cezar | Upgrade cezar. An older cezar must not write that file; step 4 exports it for a downgrade. |
| `legacy-writer` | A live older cezar serves the project, or `runs.json` changed during the import | Stop every older cezar process of the project, then restart. Nothing was imported, so the next start imports from the beginning. |
| `other` | Anything else, with SQLite's detail | Restart cezar to try again. |

A boot project that failed to open skips worktree pruning, scratch cleanup and run recovery for that start, so nothing is mistaken for an orphan; restart cezar after the fix. With `CEZ_AUTOMATIONS=1`, a project whose run store cannot open launches no automation: a due occurrence waits without counting towards the three-failure auto-pause, and fires once the store opens, within the usual one-day catch-up window. A headless `cez run` that cannot open exits 1.

Breaking: any change that makes an existing file unparseable, silently discarded, or rewritten into a new shape without reading the old one. Required path: read old + new shapes for at least one minor release (a lazy upgrade-on-read is fine since writes go through the schema), or ship an explicit migration; never require the user to delete `.ai/cezar/`.

Waits (store schema 4, hearsay-tools/cezarion#1233; human waits store schema 5, hearsay-tools/cezarion#1234; worker waits store schema 6, hearsay-tools/cezarion#1235; completion waits store schema 7, hearsay-tools/cezarion#1301; spec
`.ai/specs/2026-10-17-unified-waits.md`) live in one list on the run record:
optional `waits` (open and resolved waits; at most 16 open) and `lastWaits`
(settled waits, newest last, capped at 16), both arrays of the contract's `Wait`
(`ci`, `timer`, `worker`, or `human` with no deadline), plus `lastWaitsError` when a saved wait
could not be read. The run also keeps `automaticWakes` (timer wakes and nudges spent since
the user last wrote) and `waitDeliveryFailures` (consecutive failed wake deliveries); an
unreadable count reads as absent. They replace the CI fields `ciWait`, `lastCiWait` and `lastCiWaitError`
(#474) and the monitoring fields `monitoringWakeAt`, `monitoringWakeCapReached` and
`activity: 'monitoring'`, which are never written again (phase 3b removed the last writer, §2).
Older rows are upgraded
on read (`upgradeLegacyWaits` in `runs/store.ts`), and open rewrites every row it
loads that way:

- `ciWait` in `registered` or `parked` becomes an open `ci` wait, `wake-pending` a
  resolved one; `lastCiWait` goes to `lastWaits`, `delivered` as delivered and
  anything else as cancelled. A wait keeps its id, which is also the id of its
  wake input, so an undelivered CI result is still delivered after the upgrade.
- An agent-registered `delegation.wait` (root or worker) becomes a `worker` wait:
  `registered` or `parked` open, `wake-pending` with reason `outcome` or `timeout`
  resolved (`result.reason`), reason `cancelled` a cancelled entry in `lastWaits`.
  Its wake input (`wakeId`, else the wait's id) decides the rest: a delivered input
  makes the wait delivered, and a queued one stays queued and is recorded as the
  entry's `wakeInputId`, so the result is delivered once. The `message` stand-in is
  dropped and its input stays queued. `delegation.lastWait` goes to `lastWaits`,
  delivered when its input was delivered and cancelled otherwise. No input is added or removed.
- The completion gate's wait (`delegation.completion.waitId === delegation.wait.id`,
  schema 7) becomes a `worker` wait with `source: 'cezar'` and `via: 'completion'`,
  keeping its workers, mode, deadline and phase; an already-queued wake input is kept
  as `wakeInputId`, so its promised wake happens once, through the list.
  `delegation.wait` and `delegation.completion` are dropped.
- `activity: 'monitoring'` on a live run becomes `status: 'waiting'` (its running
  step too), with an open `timer` due at `monitoringWakeAt` when it had one. On a
  finished run the monitoring fields are dropped.
- `hasPendingHumanAsk: true` on a waiting run (the summary phase 4b removed) becomes an
  open `human` wait with `via: 'ask-line'`, `turnId: 'legacy'` and an id derived from the
  run id, unless the run already has an open human wait; recovery attaches it to the
  transcript's pending ask, so the card is not shown twice. On any other run, or when
  false, the summary is dropped. Recovery also opens such a wait for a live run whose
  transcript holds an unanswered ask with no human wait, attached to that ask. When the transcript already holds the answer (the flag was saved before it), recovery settles the upgraded wait as answered. This needs no schema bump: a schema-8 build reads the
  rewritten row correctly, because it computes the same attention from the human wait.
- An unreadable wait entry, legacy or new, is dropped by itself: the run and its
  readable waits load, `lastWaitsError` says what happened, and the status is left
  alone. Invalid wait state never reads as success.

A wait ends only when its own event fires, its deadline passes or it is cancelled,
so a terminal status write no longer clears wait state as a side effect. Human input
no longer cancels a wait either (deliberate change). Before hearsay-tools/cezarion#1233 a
human message withdrew an open CI wait, with a one-time withdrawal notice to the agent,
and a reply cleared the monitoring wake. Now the message is delivered and every open
wait keeps its deadline: a human message, Resume, a question or a permission request
cancels nothing. Each delivered turn ends with the list of waits still open, which
replaces the withdrawal notice; an agent that no longer needs a wait calls
`cezar_cancel_wait`. A run parked on a CI wait or a timer keeps one agent slot (a
monitoring slot when one is free), so its wake starts without queueing. Deadlines,
the wait id and the delivery checkpoint survive restarts; replay after ambiguous
provider acceptance remains possible, so no exactly-once guarantee is made. No new
marker or browser polling API is added.

## 4. Workflow YAML format (`packages/cezar/src/workflows/types.ts`)

Users commit these files (`.ai/cezar/workflows/*.yaml`) and share them across repos — the compact `skills:` form exists specifically to be portable. Protected shape: `name`, `description?`, and `steps` XOR `skills`; per step `id`, `name?`, agent fields (`prompt`, `skill`, `model`, `runner`, `allowedTools`, `bashAllowlist`) XOR check fields (`command`, `onFail: {retry, max}`); the `{{task}}` token; `onFail.retry` referencing an earlier step; the built-in `quick-task` name.

Breaking: renaming a key, tightening a refinement so previously valid files fail to load, changing `{{task}}` substitution, changing `onFail` semantics (retry target, `max` default of 2), or removing a `runner` value. Note the loader already degrades per file (bad files are reported in `issues` and skipped, `cez run` prints `! skipped …`) — but "your existing workflow is now skipped" is still a break. Required path: accept the old spelling alongside the new, and have `POST /api/workflows` keep writing the most portable form.

Authored agent steps may add `timeoutMs` (#470): an integer from 0 through
2147483647 milliseconds. Omitted and zero mean no wall-clock cap for managed
workflow sessions, across all runners. Skill shorthand and built-in tasks have
no wall-clock cap; standalone runners retain their 30-minute default. Save/export preserves
an explicit timeout in full `steps:` form. Check steps reject the field. A positive
limit fails the step on expiry; it does not add automatic retry or workflow resume.
Managed sessions (including Continue) separately terminate an open turn after
30 minutes without native stream/tool/heartbeat activity. Turn boundaries and
human questions pause this guard; subsequent turns and answers rearm it. This
default liveness safeguard needs no configuration and is independent of `timeoutMs`.

## 5. Skills Markdown format (`packages/cezar/src/skills.ts`)

A skill is a `.md` file with optional YAML frontmatter (`name`, `description`); the body becomes the agent's extra system prompt. Protected: frontmatter keys; the `SKILL.md`-in-a-directory convention; the discovery locations and their precedence (`.ai/cezar/skills` → `.ai/skills` → `.agents/skills` + agent mirrors → `~/.agents/skills`, `~/.claude/skills` → team repos); name-collision resolution ("the user's repo is the source of truth"); the `config.json` `skillsRepos` source shape (`{repo, ref}` — GitHub shorthand, git URL, or local path).

Built-in skills (hearsay-tools/cezarion#774, additive): the skill `source` enum gains `builtin`. A built-in ships inside cezar, lists only while its feature gate holds (today `create-cezarion-automation`, under `CEZ_AUTOMATIONS=1` with a cockpit attached), and sorts after every discovered skill, so a repo skill of the same name always wins. A consumer that switches on `source` must accept the new value.

Breaking: requiring frontmatter, dropping a discovery directory, or inverting precedence so a team skill shadows a local one. Required path: additive discovery only; a precedence change needs a README callout and a minor bump.

Since hearsay-tools/cezarion#1494 there is no zero-config team catalog. `skillsRepos` defaults to `[]`, and no team skill loads until a source is configured. The cache of a former default clone is neither read nor deleted. Upgrade note: to keep the old catalog, add `{"repo": "open-mercato/skills"}` to `skillsRepos`. An explicit `skillsRepos` loads every skill on, as before.

Each team skill has a per-project switch, stored in the project's `.ai/cezar/ui-state.json` as `disabledTeamSkills: [{repo, name}]`. The entry has no `ref`, so two refs of one repo share one switch. The off-list applies before the first-wins de-duplication by name, so switching one source's copy off lets the next source's copy of that name win. Switched-off skills are not offered and are not installed, as a root or as a companion, by any later step, live `/name` or Continue. A copy a task installed before the switch stays in that task's worktree until the task ends; cezar removes nothing from a running task. The legacy `importedSkills` key is ignored, and it stays in the file. `npx skills` installations under `.agents/skills`, `.claude/skills` and the global directories are untouched and still found as local or global skills. Removing the default source was the breaking case this section warned about. The owner requested it in hearsay-tools/cezarion#1494.

Since hearsay-tools/cezarion#1814 a later pass never rewrites or removes a skill copy in a task worktree that the agent changed or added files to. A team copy is cezar's by its content, recorded in the worktree's `cezar-manifest.json` (section 3), not by its `.cezar-team-skill.json` marker: a marked directory with no record stays as it is.

## 7. Agent event protocol (`packages/cezar/src/core/agent-runner.ts`, `packages/cezar/src/core/ui-events.ts`)

The normalized streams every runner emits — persisted to `runs/<id>.ndjson` and replayed by both the cockpit and `cez run`'s console. Two layers ship together and both are contracts; `AGENT_PROTOCOL.md` is the full spec.

- **v1 `AgentEvent`** (`agent-runner.ts`) — the flat stream. Its `type` strings (`text`, `tool-call`, `tool-result`, `image`, `token-usage`, `cost`, `session`, `turn-end`, `note`, `done`, `error`) are part of the on-disk NDJSON format and of the console renderer. Old recordings must keep replaying forever, so a v1 type is never removed or renamed.
- **v2 `UiEvent`** (`ui-events.ts`) — the normalized item-lifecycle protocol, emitted **alongside** v1 (never replacing it; a mixed v1+v2 NDJSON file is valid by design). Its dotted `type` discriminators (`session.started`, `session.ended`, `session.error`, `turn.started`, `turn.completed`, `item.started`, `item.delta`, `item.updated`, `item.completed`, `plan.updated`, `usage.updated`, `image`, `ask.requested`, plus the reserved `permission.requested` / `permission.resolved`), the `UiItem` kinds (`message`/`reasoning`/`tool`/`hook`; `hook` added in hearsay-tools/cezarion#961), and the enum vocabularies (`ToolStatus`, `ToolKind`, `StopReason`, `PlanStatus`) are the wire shape the cockpit renders and the golden fixtures pin. `ask.requested` (#473, AskUser) is emitted by the RunManager off the portable `CEZ:ASK` turn-end marker; Codex also emits the same additive event through its native `requestUserInput` bridge (#565). It is not a mapper parity capability.
- **Golden fixtures + parity** — `packages/cezar/src/core/__fixtures__/<backend>/*.expected.json` are the hand-verified contract per mapper, and `packages/cezar/src/core/ui-parity.test.ts` makes "every capability is emitted by **every** backend" executable. `BACKENDS` there lists every backend that owns a wire mapper, including pi's and omp's RPC mappers. The cockpit degrades per-capability, never per-backend; a change that lets one backend stop emitting a matrix capability is a regression, not a per-backend nicety.
- **Cross-refs** — the SSE event names carrying these (`run-event` v1, `ui-event` v2) are in section 2; the `runs/<id>.ndjson` append-only format is in section 3. The api-client's mirror (`packages/api-client/src/protocol/ui-events.ts`) is held type-exact by `packages/cezar/src/server/api-types.test.ts`.
- **Cursor transport identity (hearsay-tools/cezarion#590)** — optional `cursor-print` / `cursor-acp` step metadata selects the original wire on Continue and recovery. Older Cursor records without this field retain ACP, preserving their existing session IDs and history. New sessions use print only after the installed CLI passes the pre-inference qualification rule (hearsay-tools/cezarion#1257): a dated build version on or after `2026.10.01-e373342`, a strict `--allowed-tools` validator that lists its native tools, and every core print tool in that list. Builds that fail retain ACP. The stream and resume wire of a newer build is trusted from that check, not re-probed; the runner still fails a turn on a malformed stream or a changed native ID. A restricted print turn allows only the qualified safe tools the installed build still advertises, so a native tool a newer build adds stays denied. Every Cursor process cezar starts passes `--disable-auto-update`; a build that rejects the option runs without it. Cezar never intentionally retries a failed print resume as a fresh session, on any build; Cursor can silently lose vendor-side history under a confirmed ID.

Breaking: removing or renaming a v1 `AgentEvent` type or a v2 `UiEvent` `type`/`UiItem` kind; removing a field consumers read; narrowing an enum so a previously emitted value disappears; or dropping a parity capability from a backend. Additive is fine (new optional field, new event type — protocol v2 event types are additive by design; a new `ToolKind`/`StopReason` member is additive). Required path: read old + new shapes for at least one minor release (old NDJSON must still replay), and follow the parity requirement when adding a backend — a new runner is not compatible until it emits every matrix capability (`AGENT_PROTOCOL.md` §9). See also `AGENT_PROTOCOL.md` for the full schema, per-backend mapping, and new-runner checklist.

## 8. In-band agent marker vocabulary (`packages/cezar/src/handoff.ts`, `packages/cezar/src/runs/task-markers.ts`)

The plain-text markers the handoff contract asks every agent to emit and the engine parses from
turn text: `CEZ:DONE` (#347), `CEZ:MONITORING` (#490), and the task-reference markers
`CEZ:PR=<n>` / `CEZ:ISSUE=<n>` / `CEZ:TITLE=<phrase>` (spec 2026-07-18-task-ref-markers). These
are an agent-facing contract: skills, prompts, and running agents rely on an emitted marker
meaning what it meant when their session started.

Breaking: removing or renaming a marker, or changing what an emitted marker does (e.g. making
`CEZ:PR` gate an action instead of steering display). Additive is fine — a new `CEZ:*` marker is
inert prose to older cezars, which is the property that keeps the vocabulary forward-compatible.
The optional `pullRequests` record and summary collection retains every accepted PR
declaration and trusted creation in first-seen order (hearsay-tools/cezarion#922).
Each entry carries a number, an optional scoped GitHub URL and `declared` or
`created` evidence. Repeating `CEZ:PR` changes the scalar subject to the last
valid marker while retaining earlier associations. Scalar action gates remain
unchanged. Old records without the collection still use their legacy references;
loading does not scan historical transcripts or reconstruct missing associations.

Required path for a change: keep parsing the old spelling for at least one minor release while
the instructions emit the new one.

## 9. `~/.cezar/` per-user workspace files (`packages/cezar/src/workspace/`, `packages/cezar/src/paths.ts`)

The multi-project workspace (spec `.ai/specs/2026-07-20-multi-project-workspace.md`) adds per-user state next to the per-repo files in section 3. Same contract, one extra twist: these files are shared by **every** cezar the user runs across all their repos, so an old CLI and a new one routinely read and write the *same file* — the `.passthrough()` rule cuts both ways (an **older writer must not lose keys a newer version wrote**, not just vice versa). All paths hang off `cezarHomeDir()`, so the `CEZ_HOME` override applies (tests and containers must pin it and never touch a real home).

- **`config.json`** (`packages/cezar/src/workspace/config.ts`) — workspace config + project registry: `schemaVersion` (the migration cursor), `browseRoot` (local-folder picker boundary), `projectsDir` (clone destination), optional `modelsLocked` (only `true` makes native per-runner model settings authoritative in every project), optional `agentDefaults` (`runner`, `models` — the machine-wide agent and model a project with none of its own falls back to; absent means no opinion, which is what keeps them defaults rather than settings every repo inherits), `resources` (`maxParallel`, `memoryLimitMb`, `worktreeRetentionDefault`), `projects[]` (`{id, root, name, addedAt, lastOpenedAt, source, maxParallel?, tags?}` — `tags?` are the grouping labels the global Tasks page reads; absent means untagged, and the writers delete the key rather than storing `[]`). Every field is optional/defaulted — a bad value degrades per-key, a corrupt registry entry is dropped per-entry, never the whole array; `.passthrough()` at every object level so unknown keys survive round-trips through any version. A stored `skillsAutoUpdate` key (removed in hearsay-tools/cezarion#1494) survives merge-writes and is never read. Writes are read-modify-write merges with atomic tmp+rename, mode `0600` (dir `0700`). A corrupt file degrades to in-memory defaults with one warning and is **left on disk untouched** until the next successful merge-write replaces it. The registry is additive state that is *written, never required* — it rebuilds as projects are opened, so losing it is an inconvenience, not data loss, and no code path may ever demand its existence. `resources` is the **enforced** copy since Phase 2: the workspace semaphore (`packages/cezar/src/workspace/semaphore.ts`) caches this slice in memory (refreshed at boot and by `PUT /api/workspace/config`, never re-read per tick; a failed re-read keeps the last good snapshot, never degrading to unlimited) and applies `maxParallel` across every project's manager with the #347 waiting-run exemption intact — the per-repo keys stopped being consulted post-migration (section 3).
- **`agent-accounts.json`** (`packages/cezar/src/workspace/agent-accounts.ts`, spec `.ai/specs/2026-07-29-agent-profiles.md`) — extra config dirs for a second login of the same agent CLI, plus which one each project uses: `version`, `accounts[]` (`{id, provider, configDir, label, addedAt}`), `selections` (repo root → `{claude?, codex?, opencode?, pi?, cursor?, omp?}`), `defaults` (the machine-wide per-provider fallback a repo with no selection of its own uses). Same house rules as `config.json`: per-key `.catch` degradation, per-entry salvage for `accounts`, `.passthrough()` at every level, merge-write with atomic tmp+rename `0600`, and a corrupt file left on disk after one warning. **Its own file on purpose, and that IS the compatibility argument**: the twist named above — an older writer must not lose a newer version's keys — is a promise this repo cannot make on behalf of a build the user might switch to, and it fails outright whenever any version cannot parse `config.json` (that degrades to in-memory defaults, and the next merge-write persists them). A version that has never heard of accounts does not open this file, so it cannot drop them. Selections live here rather than on `projects[]` for the same reason, and so that deleting an account and scrubbing every reference to it is one atomic write. Accounts written into `config.json` by the branch that first shipped them are imported once and non-destructively — `config.json` keeps its keys, so an older cezar sharing the home reads exactly what it always read. Written, never required: delete the file and every project falls back to its discovered account.
- **`ui-state.json`** — the global twin of the per-repo GUI state in section 3, holding cross-project prefs (`appearance`, `notifications`, `sidebar.projectOrder`, the legacy `importedSkills` key (ignored if present since hearsay-tools/cezarion#1494, section 5; team skill switches live only in each project's `.ai/cezar/ui-state.json`), plus the legacy `sidebar.collapsed` and `lastLocation` keys the cockpit now keeps per-browser in localStorage and no longer reads here); per-project state (pinned runs, templates) stays in each repo's `.ai/cezar/ui-state.json`. Same rules as its twin: unknown keys survive round-trips, writes go through the merge path (`mergeWriteWorkspaceUiState`) with atomic tmp+rename `0600`, and a missing or corrupt file merges from `{}`.
- **Migrations** (`packages/cezar/src/workspace/migrations.ts`) — the only sanctioned way to reshape these files, and the framework contract is itself protected: migrations run **ordered** (ascending `to`), are **idempotent** (safe to re-run after a crash mid-way), **additive** (they never delete or rewrite the user's per-repo files — migration 001 imports `maxParallel`/`memoryLimitMb` and the `appearance`/`notifications` ui-state keys by *copying*, leaving every `.ai/cezar/` file in place so a downgraded cezar keeps working off its local copies exactly as before), and **non-blocking** (a failure logs one warning and boot proceeds degraded on in-memory defaults; it is never a boot failure). `schemaVersion` is persisted after **each** migration, so a crash resumes exactly where it left off; an absent version means 0 = "run everything", which idempotence makes safe. Run state is outside this framework and migrates in exactly one place: the one-time, additive import of `runs.json` into `runs.db` (hearsay-tools/cezarion#779, section 3). `runs.json` is kept for older versions and is never rewritten or deleted. NDJSON transcripts never migrate. Both keep section 3's additive-zod convention.

Breaking: renaming/removing a key or changing a default in either file; making any field required; stripping unknown keys on a write; a migration that deletes or rewrites per-repo files, or whose failure blocks boot; any code path that requires the registry to exist. Required path: same spirit as section 3 — additive first, read the old key as an alias for at least one minor release; anything more structural ships as a numbered migration that obeys the contract above.

## Single-project workspace mode — opt-in narrowing, 2026-07-21

`CEZ_SINGLE_PROJECT=1` deliberately narrows the multi-project workspace to the repository passed
to `cez serve`. Activation is strict: only the exact string `1` enables the mode; `true`, `yes`,
an empty value, and an unset variable all preserve the default multi-project behavior.

- **Intentionally narrowed under the flag**: `GET /api/health` and `GET /api/projects` expose only
  the launch project; `POST /api/projects`, `POST /api/projects/checkout`,
  `PATCH /api/projects/:projectId`, `DELETE /api/projects/:projectId`, and
  `GET /api/fs/browse` answer `409` before side effects.
  The equivalent `cez projects add` and `cez projects remove` commands refuse with exit code 1.
  The cockpit consequently omits cross-project navigation, add-project controls, the global
  Projects settings section, and the New Task project picker.
- **Unchanged by default**: without the exact opt-in, every section 2 route, response, CLI command,
  registry behavior, and cockpit affordance retains its multi-project contract. This is a
  capability mode, not a new default or a persisted workspace setting.
- **Non-destructive rollback**: the mode never deletes, rewrites, or migrates project rows in
  `~/.cezar/config.json`. Unset `CEZ_SINGLE_PROJECT` and restart the server to reveal the full
  registry again; no manual repair or state migration is required.
- **No deprecation alias**: no previously accepted input or default behavior changed. The explicit
  flag is the boundary authorizing the narrower protected surface, and removing it restores the
  protected default wholesale, so an old-spelling compatibility window would serve no purpose.

GitHub automations (spec `.ai/specs/2026-07-25-github-automations.md`) shipped gated only by forge

## One turn-end rule (hearsay-tools/cezarion#1234, phase 2b) — deliberate, 2026-10-19

The markers keep their meaning (section 8). What changed is what a turn end does when it carries
no wait, no question and no done. Spec: `.ai/specs/2026-10-17-unified-waits.md`, "The turn-end
rule" and "Phase 2b decisions".

- **A turn end with no wait costs one more turn.** Cezar sends the no-wait nudge, which spends one
  unit of the automatic-wake budget. If that turn also ends with no wait, or no reply comes within
  5 minutes, Cezar opens its own `no-wait` human wait and the run reads Needs you. Before, the run
  parked `waiting` at once, so a webhook or `cez task watch` now sees `waiting` one turn later. An
  owned worker still parks plain after its nudge.
- **Prose no longer raises Needs you.** A question or review request in prose, beside the
  monitoring line, live workers or another wait, used to raise the prose gate. Now the run parks
  on those waits. With no wait, it gets the nudge. An agent asks with `cezar_ask` or the ask line.
- **A rejected ask line registers nothing.** Its diagnostic note and raw text stay, and the turn is
  one with no wait, so it gets the nudge. A worker whose nudge reply also registers nothing now
  settles `done`, not `failed` with `invalid structured question`.
- **An autonomous run's ask line before the budget is not registered.** Its note changes from
  `autonomous — question overridden by the auto-continue nudge: …` to
  `autonomous — question not registered; continuing: …`.
- **The final-message nudge is the no-wait nudge.** Its notes and heartbeat change to the no-wait
  nudge's: `no wait or done — reminding the agent once (n/40)`,
  `no reply to the no-wait nudge — waiting for you`, and `status=running (no-wait nudge)` in the
  handoff journal. A consumer that matched the old note text must match the new text. (Since
  hearsay-tools/cezarion#1809 the handoff journal carries no heartbeat line at all.)
- **The `unstructured-human-gate` note code** now marks the gate that a human wait without a card
  raises (the monitoring line with re-checks off). Older transcripts carry it for the prose gate.
  Both are answered the same way, so no record migrates.
- **Dry run.** The native mocks answer the nudge with a `cezar_ask` card, so a dry-run task parks
  on a question after one extra turn. `CEZ_MOCK_NUDGE_REPLY=plain` makes them answer in plain text.
- **Finish closes an open question (hearsay-tools/cezarion#1260, additive).** An accepted Finish
  appends a new event, `human-ask-closed`, with the closed question's `askSeq` and
  `reason: 'finish'`. It retires the question as `human-input-delivered` does, but nobody answered
  it, so no delivery is recorded. A reader that skips event types it does not know sees the
  question still open on a finished run, as before this change. Stop appends nothing and keeps
  the question.

## When in doubt

If a change might break any surface above, say so in the PR description, label the PR `risk-high`, and route it through the review + QA gates in `SDLC.md`. A silent break found in review is a blocker per `CODE_REVIEW.md`.

### Bounded structured-question recovery (#88)

A CEZ:ASK payload missing only closing braces/brackets after a complete structural value gets one bounded repair, then the existing schema validation. Mid-string truncation, mismatched delimiters and invalid question structures remain rejected. Fresh and continuation turns persist a danger note for recovery or rejection; a recovered card warns users to check the options and how many they may pick, since repair cannot restore missing meaning. The raw recovered marker stays in the audit stream until the cockpit hides it alongside a validated card, preserving rejected split-stream fallback. Existing and unknown note tones stay dim. DONE/ASK precedence, Claude wakeups and monitoring serialization are unchanged.

Parent/worker conversation protocol additions are optional on old records: root metadata may carry `conversation`, both roles may carry request-aware `wait`/`lastWait`, and `AgentInput` may carry structured `conversation` attribution. Send/follow-up/reply accept the strict conversation send contract (`id`, `recipientRunId`, `kind`, optional `requestId`, `text`, defaulted `timeoutSeconds`) and return message, delivery, and optional outcome. Inspection accepts `{recipientRunId}` and returns the pair's messages/outcomes; cancellation accepts `{requestId}` and returns its settled outcome. Request waiting shares `POST /api/v1/delegation/wait` and accepts `{requestIds, mode?, timeoutSeconds?}` and returns the existing wait result envelope. Conversation authorization is limited to a root and its direct owned worker, with no peer or worker-control grant. Request selection is additive to lifecycle wait receipts; the original worker-ID CLI form and route stay valid. Persisted `conversation-message` and `request-outcome` projections use stable IDs and do not enqueue on replay. Accepted messages deduplicate durably, while provider acceptance/checkpoint crashes retain delivery ambiguity. These private routes share the existing opt-in transport and introduce no environment settings or automatic terminal continuation.

### Asynchronous project metadata (#662)

The GitHub list returns before optional board discovery/memberships finish. Additive
`projectsState` (`refreshing`, `ready`, `unavailable`) and `projectsGeneration` fields
identify freshness. Retained `projects` and issue `projectIds` are previous verified
values while refreshing or unavailable; absent `projectIds` means unknown, never no
membership. `GET /api/v1/github/projects?generation=<uuid>` (and its project-scoped
alias) awaits that list generation's bounded lookup and returns `{generation, state,
projects?, membership?, reason?}`. Expired generations return unavailable without
starting another lookup. Clients apply only matching generations and preserve filter
selection until authoritative metadata arrives.

### Resume request deadlines (hearsay-tools/cezarion#1241)

Resume requests accept an explicit `timeoutSeconds` up to 86,400 seconds. The
600-second default and the 1,800-second cap for ordinary requests and waits
remain unchanged. A first explicit reply after deadline expiry changes the
recorded `timed-out` outcome to `replied-late`; other settlements stay final.
Transcript consumers accept a separate outcome amendment projection, replacing
only `timed-out` with `replied-late`. Existing timeout projections remain valid.
