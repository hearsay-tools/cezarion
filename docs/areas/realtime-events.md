## Rules

Browser ownership: read `.ai/specs/2026-10-08-browser-tab-coordination.md` first. Local visible documents share one same-origin SharedWorker for the workspace SSE, multiplexed task SSE, topic WebSocket and allowlisted recurring reads; documents retain their own caches/cursors. Hidden documents release demand; authenticated bootstrap, scope reconciliation and bounded history hydration precede restoration. Remote/failed-worker mode uses finite authenticated HTTP (no permanent SSE or ordinary WebSocket). Two live channels: the SSE run/event stream (`/api/v1/workspace/events`, `packages/web/src/api/global-events.tsx`) and the **WebSocket subscription bus** (`/api/v1/ws`, `ws` lib server-side, native `WebSocket` client). The bus is the pattern for any new live signal instead of a `refetchInterval`. Its whole discipline is **demand-driven subscription**: a topic's server publisher starts on the `0→1` subscriber and stops on `1→0`, and one socket per local coordination group ref-counts listeners per topic. A subscribe answers with the publisher's snapshot first: the hub holds that subscriber's publishes until its snapshot is sent or fails, then sends them in order, so an older snapshot never replaces newer published data (hearsay-tools/squawk#3443).

**Subscribe at the scope that matches the data's demand lifetime, always return the unsubscribe (`useEffect(() => subscribeTopic(...))`), publish only on change** — a leaked subscription is a server publisher that never stops AND a component that keeps waking for a screen the user left. Per-view signals subscribe in the view; **session-global signals subscribe ONCE at the root**, not per reader — health is the worked example: one `useHealthSubscription()` controller in `GlobalEventsProvider` subscribes after bootstrap only for local mode, while `useHealth()` is a pure cache read the ~15 readers call without touching the socket. Remote mode must open no browser WebSocket because it cannot explicitly carry reverse-proxy credentials; it uses finite authenticated HTTP reconciliation. One socket per local coordination group — never `new WebSocket` for a feature; add a topic.

**One named exception: the live preview pane** (hearsay-tools/cezarion#781, spec `.ai/specs/2026-10-02-live-preview-v1.md`) opens its own `/api/v1/p/:projectId/runs/:id/preview/ws` per open pane, in remote mode too, because it streams binary JPEG frames and pointer input that a JSON topic cannot carry. It is opt-in behind `HSQ_PREVIEW=1` (`CEZ_PREVIEW` fallback) (off, the path answers 404), demand-bound to an open pane, refused before the handshake unless the upgrade guard trusts it, and capped at two upgrade attempts so a proxy that cannot carry it (Basic Auth, open-mercato/cezar#688) shows 5.14 instead of looping. A new feature does not get the same exception: add a topic. Liveness: server ping/pong reaping + app-level beat, client watchdog + reconnect. Topics are workspace-level (single-mount, never `/api/v1/p/`) and, because the upgrade guard admits any loopback origin (WS has no CORS), must only carry data safe for any local page — read the spec's security caveat before adding one.

**Activity topics.** The Activity view (`.ai/specs/2026-11-05-live-activity-view.md`) uses two topics on the bus: `activity:project:<projectId>` for one project and `activity:workspace` for all projects (`packages/cezar/src/server/activity-topic.ts`). The project topic is a **topic family**: one registration for the prefix, and one publisher for each concrete name, started on its first subscriber and stopped on its last. A project id never holds a colon, so the names cannot collide. Both topics are **trusted only**: they keep the default `loopbackReadable: false`, because they carry run titles, tool titles and request text. Both are **demand-driven**: a publisher sends a full snapshot on subscribe, then a new snapshot only when something changed, at most every 500 ms. While it has subscribers, it also checks the foreign claims every 5 s, because another process's writes send no change event. With no subscriber, nothing runs. Without topics (remote mode, or no working SharedWorker), the view uses the **finite fallback**: it reads `GET /api/v1/workspace/activity` every 5 s while the document is visible, through the shared recurring reads. Each HTTP read also marks the project's demand for 15 s, so CI check progress stays fresh for a fallback reader.

**Workspace stream summary mode** (hearsay-tools/cezarion#2730, plan `.ai/specs/2026-11-06-cockpit-performance-plan.md` § S1). `GET /api/v1/workspace/events?runs=summary` carries list rows instead of full run records. Without the parameter the stream is byte-identical to the legacy stream (`workspace-events.test.ts` checks it), so older tabs, older shared workers and scripts keep working. The cockpit always opts in, and the shared worker name and `LIVE_PROTOCOL` changed with it, so an old worker never feeds a new document. They changed again with the patched runs index (version 3, `cezar-live-v3`, hearsay-tools/cezarion#2729): a new document relies on its worker's late-subscriber `ready`, which a version-2 worker kept alive by an older tab never sends. The contract is `packages/contract/src/workspace-events.ts`. One feed per server (`packages/cezar/src/server/workspace-run-feed.ts`) subscribes once to each project store, numbers the frames and builds each frame's text once per mode; every connection writes the cached text. With no connection open, the feed holds no store, bus or usage subscription, so it numbers only the events it hears while a connection is open.

- **Frames.** `run-summary` is `{ project, seq, run, relationships }`: `run` is exactly the `/workspace/runs-index` row (`toRunSummary` plus the live usage sample), and `relationships` is a digest of the fields `/runs/:id/relationships` renders. `run-deleted` is `{ project, seq, id }`. `ready` is `{ generation, seq }`. `usage` keeps its shape, and summary mode also sends one empty `{ project, usage: {} }` when a project's last live row stops.
- **Ordering.** The feed gives every `run-summary` and `run-deleted` one process-wide `seq`. Within one connection and one `generation`, the numbers a client receives are contiguous across projects, starting after `ready.seq`. A jump means lost frames: the cockpit applies the frame, then reconciles as after a reconnect. A new `generation` is a reset, and a reopened connection takes a new baseline; neither is a gap. The shared worker sends a document that opens a new workspace subscription late, or rejoins after a server restart, a `ready` with the stream's generation and the last frame number already delivered, before any other frame; the ping after it still marks the attachment live (hearsay-tools/cezarion#795). The worker keeps that generation per document: a demand change that only moves the document's epoch sends no new `ready`, so a frame the document dropped under the old epoch still shows as a gap. `seq` rides in the data, not in the SSE `id:`, because the stream has no replay.
- **Snapshots.** `GET /workspace/runs-index` answers `generation` and `eventSeq`. The route reads `eventSeq` after its last `await` and before its synchronous reads, so every frame at or below it is in the snapshot and every frame above it is newer.
- **Detail.** A summary never stands in for a full record. On `run-summary`, an observed task detail drops its Finish verdict and fetches at once when no fetch is in flight, then at most once more per 400 ms. A response from a fetch that started before the latest event never restores the verdict. An unobserved cached detail drops its verdict and is marked stale without a fetch. A worker's event keeps the parent's trailing refresh.
- **Index.** The cockpit patches the cached `GET /workspace/runs-index` answer from the stream (hearsay-tools/cezarion#2729, plan § S5). The pure rules are in `packages/web/src/api/runs-index-cache.ts`; `packages/web/src/api/runs-index-sync.ts` wires them to the query cache. Rows are keyed by `(projectId, id)`, and a row comes only from a snapshot or from a frame's `run` plus its `project`. Root-only membership: a worker row never enters. An update replaces the row in place (the old object stays when the rows are deep-equal); a create inserts at its `createdAt` position; a delete removes the row. Archive and unarchive are exact for a complete project. In a project listed in `truncated`, a change that moves the archived window boundary is patched, then reconciled. A row such an index does not hold is placed by the window edge (the oldest held archived row): an unarchived row older than the edge came from beyond the window and is inserted, then reconciled; a newer one is a create and is only inserted; an archived row newer than the edge enters the window and is inserted, then reconciled; an older one stays out. Remaining limit: a `run-deleted` for a row the index does not hold cannot be placed (it may be a worker), so a `truncated` it made stale heals at the next reconciliation or backstop read. `usage` ticks of any project replace that project's row samples; an empty tick clears them. `project-removed` and a registry id that disappears drop the project's rows, its `truncated` entry and its `referenceStatuses` with no request. Patches never touch `referenceStatuses`; only a snapshot refreshes them. Patches are written to the cache at most once per 250 ms: the first patch after a quiet period lands in the next animation frame (or within 100 ms in a document with no frames), and later ones wait for the end of the interval, which never restarts, so sustained events stay visible. Every index write re-renders the app shell; the bound is a measured correction of the plan's "once per animation frame" (cold bootstrap, closed project view: 191 commits per frame write against 25 with coalesced writes; `docs/performance/runs-index-patching.md`).
- **Index fence.** Every frame records the generation of the stream that delivered it, from that stream's `ready`. A frame of unknown generation (after a new attachment and before its `ready`) is not applied. On the shared feed the document then asks its worker for the `ready` once (`workspaceReady: true` on every sync until a `ready` arrives; the demand stays, so the shared stream never restarts), for example when an epoch change made it drop its first `ready`. That `ready` names the last frame the stream delivered: a frame the document missed shows as a gap and reconciles as any gap does, and the index is read once for the frames it skipped. Without a shared feed it asks for one fenced reconciliation. A queued patch, run or usage, applies only to cached data of its own generation. Each document keeps an overlay of the newest frame per row key, deletes included, each with its generation; a merge uses only the frames of the snapshot's generation. Every snapshot (the query function, the shared live read through `useLiveRead`'s merge hook, each reconciliation) passes `mergeIndexSnapshot`: a frame above `eventSeq` is laid over the snapshot, and frames at or below it leave the overlay. A stream `ready` with another generation drops the frames of other generations. A snapshot from another generation than the stream's stays unpatched and asks for one reconciliation per such generation, so a stream that stays down cannot cause a read loop. A snapshot older than the frames the overlay still covers asks for one more reconciliation. A cold cache records frames in the overlay but is never created by them; the first read merges them.
- **Index reconciliation.** A full index read runs only on bootstrap (first open), reconnect, visibility restore, a `seq` gap, a frame of an unknown project, a truncated boundary move, `project-added`, `project-ready`, a new registry id, and the visible-only backstop read: 60 s by default through the shared live read, or the shorter interval a page asks for (the global Tasks page keeps its 15 s). At most one reconciliation runs at a time, plus one trailing read. Event-driven triggers hold 400 ms and then fire; the hold never restarts, so sustained events cannot postpone it. Remote mode keeps its 5 s full reconciliation.

**Report shelves.** `reports:project:<projectId>` is a trusted-only topic family
(`server/reports-topic.ts`, `loopbackReadable: false`). A mounted shelf owns its
subscription. Its first subscriber starts the report index watch; its last release
stops the watch. Subscribe sends `{type: 'snapshot', epoch, generation,
metadataGeneration}`. Content changes increment `generation`; searchable/displayed
task changes increment `metadataGeneration`. Changes coalesce for 500 ms. Metadata
frames carry the latest `{runId, taskTitle, taskStatus}` per changed task; content
frames require a list reconciliation. The finite twin is
`GET /api/v1/p/:projectId/reports/state`, every 5 s while visible; each read holds
15 s of watch demand. Both transports compare all three counters. A shelf fences
in-flight content/search reads and replays concurrent metadata patches onto
unfiltered responses. Unrelated workspace events do not invalidate report shelves.

**Home recovery.** The trusted-only `home:recovery` topic carries the same snapshot
as `GET /api/v1/home/recovery`. One root subscription serves the banner. The server
holds filesystem watches only while there is demand, including per-file journals
so an acceptance from another cockpit is visible without a primary-file write.
Unchanged snapshots produce no frame. The central live coordinator supplies finite authenticated reads when SharedWorker topic delivery is unavailable, as for other live-backed queries. Recovery adds no timer of its own.
