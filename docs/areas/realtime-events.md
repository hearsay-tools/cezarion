## Rules

Browser ownership: read `.ai/specs/2026-10-08-browser-tab-coordination.md` first. Local visible documents share one same-origin SharedWorker for the workspace SSE, multiplexed task SSE, topic WebSocket and allowlisted recurring reads; documents retain their own caches/cursors. Hidden documents release demand; authenticated bootstrap, scope reconciliation and bounded history hydration precede restoration. Remote/failed-worker mode uses finite authenticated HTTP (no permanent SSE or ordinary WebSocket). Two live channels: the SSE run/event stream (`/api/v1/workspace/events`, `packages/web/src/api/global-events.tsx`) and the **WebSocket subscription bus** (`/api/v1/ws`, `ws` lib server-side, native `WebSocket` client). The bus is the pattern for any new live signal instead of a `refetchInterval`. Its whole discipline is **demand-driven subscription**: a topic's server publisher starts on the `0→1` subscriber and stops on `1→0`, and one socket per local coordination group ref-counts listeners per topic.

**Subscribe at the scope that matches the data's demand lifetime, always return the unsubscribe (`useEffect(() => subscribeTopic(...))`), publish only on change** — a leaked subscription is a server publisher that never stops AND a component that keeps waking for a screen the user left. Per-view signals subscribe in the view; **session-global signals subscribe ONCE at the root**, not per reader — health is the worked example: one `useHealthSubscription()` controller in `GlobalEventsProvider` subscribes after bootstrap only for local mode, while `useHealth()` is a pure cache read the ~15 readers call without touching the socket. Remote mode must open no browser WebSocket because it cannot explicitly carry reverse-proxy credentials; it uses finite authenticated HTTP reconciliation. One socket per local coordination group — never `new WebSocket` for a feature; add a topic.

**One named exception: the live preview pane** (hearsay-tools/cezarion#781, spec `.ai/specs/2026-10-02-live-preview-v1.md`) opens its own `/api/v1/p/:projectId/runs/:id/preview/ws` per open pane, in remote mode too, because it streams binary JPEG frames and pointer input that a JSON topic cannot carry. It is opt-in behind `CEZ_PREVIEW=1` (off, the path answers 404), demand-bound to an open pane, refused before the handshake unless the upgrade guard trusts it, and capped at two upgrade attempts so a proxy that cannot carry it (Basic Auth, open-mercato/cezar#688) shows 5.14 instead of looping. A new feature does not get the same exception: add a topic. Liveness: server ping/pong reaping + app-level beat, client watchdog + reconnect. Topics are workspace-level (single-mount, never `/api/v1/p/`) and, because the upgrade guard admits any loopback origin (WS has no CORS), must only carry data safe for any local page — read the spec's security caveat before adding one.
